# 13 分點排行與追蹤(規劃;2026-07-07 使用者需求)

> 目標:一張「值得追蹤的分點」排行表 + 「這些分點在最近可用交易日買賣什麼」動向表,含權證分點視角。
> 本文件把 04 §2–5(分點模型)與 09(足跡)落成**可直接開工的功能規格**。
> **前提:分點資料尚未解鎖**(見 §6)。資料一到位,本規格即可實作,無需再議。

## 1. 功能一句話

盤後自動回答兩個問題:
1. **誰值得追?** —— 分點可信度排行榜(演算法算出高勝率、會賺錢、非隔日沖的分點)
2. **他們最近交易日買賣了什麼?** —— 追蹤名單分點的每日進出明細(股票 + 權證)

### 2b. 演算法自動入選(每週六重算,04 §5 可信度分數)

入選條件(全部滿足):
1. 近 2 年「進場事件」≥ 10 次(事件 = 單股單日淨買超 ≥ 該股成交值 1%,連續日合併)
2. 可信度分數 ≥ 70(構成:5 日勝率 30% + 平均報酬 25% + 買點分位 15% + **規模 10%** + 近 90 日仍有效 20%)
   > **2026-09-03 更正**:本行原寫「非隔日沖 10%」,與 §3b 的公式及 `compute_branch_stats` 的實作皆不符——可信度分數裡**沒有**隔日沖項,第四項是近 90 日買超總金額的 log 級距(規模)。隔日沖只作為 §2b-3 的獨立閘門與榜單切分,不進分數。
3. **非隔日沖——2026-09-03 起改以「配對比例」判定(見 §8)。** 舊定義「買超次日回吐 ≥70% 的比率 < 60%」是把一個分點**跨全部個股**的觀察 pooled 成單一比率;一個分點平均橫跨約 1,128 檔,該比率永遠到不了 60%,實測 831 個分點**無一成立**,等於這道條件從未真正生效。新規則:`is_daytrade = 1` 才擋自動入選;**`NULL`(可判定配對 < 20,即「無法判定」)不擋**——多數分點屬此類,若把它當成擋人條件,自動入選將幾乎永不發生。
4. 近 90 日仍活躍(事件 ≥ 2)

自動移出:連續 60 日可信度 < 50 或不活躍。`source='auto'`,與手動名單並存,UI 標示來源。

## 3. 排行榜演算法(每日/每週計算)

### 3a. 分點×個股統計(`branch_stock_stats`,05 已定義)

每事件記錄:進場日、均價(以次日開盤計,避免 T+1 偷看)、張數、金額、後 1/3/5/10/20 日報酬。
彙總:事件數、勝率(5日>0)、平均/中位報酬、最大回撤、買點分位(買在近 20 日區間低點程度)、隔日沖率、持有型態(短線/波段)。

### 3b. 分點總排行(跨個股彙總)

```
排行分 = 0.30×勝率(40%→0分,70%→滿分)
       + 0.25×平均5日報酬(0%→0,+5%→滿分)
       + 0.15×買點品質(買低分位)
       + 0.10×規模(近90日買超總金額,log 級距──太小的分點統計無意義)
       + 0.20×近效性(近90日 vs 全期報酬衰減)
隔日沖判定成立 → 單獨列「隔日沖分點榜」,不進主榜(它們是反指標/風險訊號來源)
```

> **2026-09-03**:「判定成立」現指 `is_daytrade = 1`(配對比例達門檻,見 §8)。**未判定(`NULL`)一律進主榜**,不視同成立——匯出端的 detail set 過濾已由 `AND is_daytrade = 0` 改為 `AND COALESCE(is_daytrade, 0) = 0`,因為 SQL 三值邏輯會把 NULL 列**靜默丟掉**。主榜／隔日沖的切分亦改為顯式比對 `== 1` / `!= 1`。

### 3c. 權證分點(同一套,兩個差異)

1. **資料面與跨權證彙總**：權證代號理論上為獨立個體，但因一檔熱門股票常同時有多檔權證發行，分點大戶通常會分散買進多檔。故實作上以「標的股」為中心，將單一分點對同一標的下「所有權證」的買賣張數，乘上該日權證收盤價，加總出該分點對該標的的「權證淨買賣金額」。
2. **統計面與時間維度**：為了捕捉大戶在不同週期的佈局，我們將時間維度切分為 **1D / 2D / 5D / 30D / 120D**。全市場 `/branch` 探索仍以 `abs(淨買賣超) >= 500 萬` 作大額門檻；個股詳細頁是較寬的證據視角，先讀 `branches/warrant-stock-details/index.json`，再依股票讀取 `{stock_id}.json` 分片，以 `>=100 萬` 顯示，100–499 萬只標「觀察」、不視為全市場大額訊號。兩者皆明示熱門上市權證與每檔前 15 大分點裁剪限制。

### Tab「分點最近交易日進出」(核心使用場景)
`branches/today.json` v1 = `{version: 1, as_of, movements}`。export 以價格日為上限，取**追蹤分點實際存在的** `MAX(branch_trades.date)` 作 `as_of`，再列該日全部 tracked movement；無資料時為 `as_of: null, movements: {}`。前端仍接受舊 bare mapping（code 先於 data 部署時不冒稱日期）。

每列為分點｜股票（點入個股頁）｜買進張｜賣出張｜淨買賣張｜佔比；買進／賣出是中性 gross 值，淨值正紅、負綠、零中性，`pct=null` 顯示「—」。保留最近可用分點資料日，不以價格日或「今日」冒稱。排序沿用分點後淨買賣；高可信度分點與綜合分的交集只可作 UI 提示，不變更 04 §2 B5 給分。

### 分點視角頁(點任一分點)
近 90 日操作時間軸(買賣超 × 股票)、績效統計卡、擅長產業/題材分布、在追蹤個股上的 K 線足跡連結(09)。

### 分點逐日明細的 bounded 聯集（2026-08-31 已落地）

`branches/track/index.json` 的 detail set 不再只限 `tracked_branches`：它是所有 tracked 分點，聯集最新 `branch_rankings` 快照中 `is_daytrade=0`、依 `rank_score DESC, samples DESC` 的前 100 名。去重時 tracked source 優先；只因排行入選的分點保留 `candidate`／`auto` 等來源並可產 lazy shard。這不改排行、統計、分數、資料表或追蹤 seed。

三層 hard cap 為 ranking Top100、聯集最多 200 branches、每 shard 最多 20,000 rows。tracked 分點本身若超過 200，export fail closed，絕不靜默省略；尚有容量才依排名順序加入 ranking-only。每 shard 限在 export date 以前的 120 日視窗；即使 `daily_prices` 無法提供裁切下緣，仍只保留最新 20,000 rows 並標 `truncated`。payload `as_of`、index `first_date`／additive `last_date` 均取實際資料列日期，沒有 rows 的 tracked shard 仍存在且三者皆為 null。前端可讀舊 index／shard；只有 ready index 命中的排行卡才可下鑽，其他如實標「僅有排行」。索引或 shard contract/fetch 失敗不能偽裝成 empty，排行榜仍可使用；empty 只表示該 120 日視窗未進每日前 15 大買／賣超，不代表沒有交易。

發布前唯讀容量 evidence：排名 831、舊 history index 47；`華南永昌-大安` 排第 8、近 120 日依現行口徑有 4,887 rows，但原本僅是 candidate。tracked+非隔日沖 Top100 聯集為 138 分點／599,525 rows，估約 22.9 MiB；這是當次估算，不是對未來資料量的保證，實際上由三層 hard cap 約束。其後已受控同步、export/deploy；正式 index 為 138，該 shard 實際為 4,824 rows／83 交易日。未改 DB／cron。

## 7. 誠實限制(UI 要標)

1. 分點資料 T+1 或更晚；「分點最近交易日進出」必顯示 export 的 `as_of`，不可用價格日或「今日」替代。
2. 分點 ≠ 單一人:大分點混雜多帳戶,統計是機率不是身分證。
3. 勝率以「次日開盤進場」計算,與分點實際成本有差。
4. 名單公開的知名分點常被跟單,訊號會衰減——近效性權重 20% 就是為此設計。
5. **隔日沖徽章是「看得見的比例」,不是行為比例。**(2026-09-03)一筆配對只有在「次日該分點又出現在該股當日**前 15 大賣超**」時才算翻單。真正的隔日沖 desk 幾乎全數當沖出場,但每日只公布前 15 大,多數出場看不見——所以連台股最公認的隔日沖分點(凱基-台北)實測也只到 **0.315**,而非接近 1.0。**今日資料的可觀測上限約 0.33。** 徽章必須讀作「**可判定的分點×個股配對中,在每日前 15 大切片內看得到隔日翻單的比例**」,是**下限**;文案**絕不可**寫成「多數情況下隔日出場」。

### 8.1 2026-09-03 實測結果與定案（V2 提案有一半是空的，真問題在別處）

以 WP-B4 還原出的 2026-08-28 正式副本實測後，上面的 V2 提案**部分被推翻**：

- **成熟度級距在分點層級是惰性的，不採用。** 831 個分點的 `matured_samples` 中位數為 **3,708**（min 5、p90 7,975、max 132,015），落在 `<10` 的只有 **1 個**、`<30` 只有 **5 個**——`10`／`30` 比中位數低了三個數量級。「<10 不評分」的三種讀法（仍評分只標記／列榜但無分數／不列入）名次漂移**全為 0**，彼此只差 1 個分點。pair 層級同樣不採用：配對不排名、不評分、不顯示，加級距只是裝飾，且依構造約九成會落在 insufficient。
- **`samples` 混淆確實存在，且已修。** 新增 `matured_samples` 欄位（見 §5），前端「樣本不足」徽章改讀 `matured_samples ?? samples`。實測 819／831 個分點兩者不等，但差距中位數僅 62、平均 91，相對於中位 3,708 的分母約佔 1.7%。
- ⚠️ **撤回「隔日沖最低觀察數改 8 是 no-op」的說法。** 該結論是在**分點層級**量到的，而該層規則本來就恆為 false，故量不出差異。在 **pair 層級**，最低觀察數由 4 提到 8 使可判定配對池由 937,856 縮到 **139,076（14.83%）**、被標記配對由 **5,120 降到 2,236（−59%）**。**不得再引用分點層級的數字作為 pair 層級的證據。**
- **真正的缺陷不在提案裡：門檻套錯層級。** pair 層級每個配對平均只有 **4.97** 個事件，規則在此會觸發（5,118／937,856 ≈ 0.55%）；但一個分點平均橫跨約 **1,128** 檔股票，pooled 之後任何門檻都被稀釋。同理前端 `MIN_SAMPLES = 10` 的徽章在正式資料上只對 1 個分點生效（`samples` min = 7）。而 `branch_stock_stats.is_daytrade_suspect`——唯一真的有訊號的那一層——**寫了卻沒有任何消費者**（無 export、無 UI、無 gating）。

**定案（依 `AGENTS.md` 高風險流程，由使用者委由 Fable 5.1 決定；使用者已批准上線）：**

| 常數 | 值 | 買到什麼 |
|---|---|---|
| `DAYTRADE_MIN_OBS` | **8** | pair 層級，合併連續段**之前**的觀察數;不足記 `NULL` |
| `DAYTRADE_MIN_PAIRS` | **20** | 分點層級可判定配對下限;不足記 `NULL` |
| `DAYTRADE_PAIR_SHARE` | **0.20** | `flagged / determined` 達此比例即 `is_daytrade = 1` |

`20` 的取捨是機率而非直覺：pair 層級基準率約 1.5%，若下限取 10，只要 2 個 flagged 就跨過 0.20，`P(>=2/10) ≈ 0.94%`，乘約 800 個分點約 **7.5 個偽陽性**（多於真陽性）；取 20 需 4 個，`P(>=4/20) ≈ 2.4e-4`，全榜期望約 **0.2 個**。

`0.20` 的取捨見 §7-5 的可觀測上限：初擬的 `0.5`（「多數時候翻單」）實測**標記 0 個分點**，等同重現它要修的缺陷。0.20 高於 p99（0.1221）、約 p90（0.0213）的 8 倍，且約為觀測上限的三分之二。**這兩個常數由 2026-08-28 的分布推導而來，不是行為定義**；資料源或截切方式改變時必須重新校準。

**上線驗收**（精確重算，非代理指標）：min_obs=8 得可判定配對 **164,569**、被標記 **2,236**（1.36%）;分點層級 `determined >= 20` 者 **799**、落 `NULL` 者 32;share p50 **0.0000**、p90 0.0213、p99 0.1221、max **0.3152**。`share >= 0.20` 恰好標記 **3 個**：凱基-台北 615/1951 = 0.3152、群益金鼎-大安 57/197 = 0.2893、元大-三峽 23/80 = 0.2875。最接近落選者為元大-竹科 84/467 = 0.1799、凱基-宜蘭 8/51 = 0.1569、群益金鼎-台北 9/60 = 0.1500——它們**仍留在主榜並顯示自身比例**，供使用者自行判斷。

### 8.2 E2 point-in-time 帳本的粒度定案

同批決定：point-in-time 結果**只在分點層級持久化**（`branch_pit_stats`，見 §5）。分點×個股粒度以算術排除——9 個 as_of 就涵蓋 945,131 個實體、5.07 GB，約 250 個 as_of 將達 ~140 GB，而 VPS 僅 29G;市場層級則是分點列的欄位加總（rate 穩定到 `53.283864%` → `53.292160%`，相差 0.008 個百分點），讀取時 pool 即可，不需要表。

**存計數不存比率**的理由是可還原性：同一個 `low_buy_rate` 各日平均 75%、pooled 66.7%，差距純由分母加權而來;且真實資料中 **24.3%** 的 buy episode 沒有已知分位、**約 25%** 的 `fwd5` 未成熟——裸 rate 會把四分之一的資料藏起來。

**持久化而非每次重跑**的理由：工具讀的是 `branch_trades WHERE date <= as_of`，而 490 日回補**正在改變過去日期的查詢結果**;帶 `computed_at` 的列是「我們在第 X 天看得到什麼」的唯一紀錄。**注意事後回補的列不具備此性質**——`computed_at` 誠實標示它們是「今天對過去的看法」。
