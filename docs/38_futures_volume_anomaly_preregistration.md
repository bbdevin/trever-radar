# 38. 個股期貨成交量異常 —— 事前登記(統計量、否決條件、全案否決)

> **地位**:本文件是**事前登記**(pre-registration)。它的效力來自時間順序,不來自內容有多聰明:
> 它必須在任何人查詢過 `futures_daily` 的回補資料之前 commit。撰寫當下 `futures_daily` 只有
> 2026-09-15 一天(1,969 列個股期貨,已用於 export),250 交易日回補正在進行;撰寫者
> (決策者與執行者)都沒有對回補資料下過任何查詢。
>
> **凍結規則**:本文件 v1 的每一個數字與每一條規則,在回補資料可見之後**不得修改**。
> 要改,只能開 v2,而 v2 只能用 **v2 commit 之後才出現的交易日**重新取得資格(同 `docs/04`
> §2 事後分位的再資格化規則)。「跑出來不好看所以放寬」正是這份文件要擋的事。
>
> 使用者原話:「幫我增加期貨成交量異常的股票 我想要期貨成交量比之前平均多的 列出來
> 可以拿來做判斷籌碼或是技術分析成交量的依據」。本文件把「比之前平均多」翻成一條可
> 重現、無分母、人看得懂的規則;把「拿來做依據」翻成一個能證偽的檢定。

## 0. 名詞

- **契約**:`futures_contracts.contract_code`(例 `CCF`)。同一檔股票可能有兩個契約
  (2,000 股標準型與 100 股小型,例 1565 的 MYF/OMF)。**一切以契約為單位計算**,
  個股頁只是把契約的結果掛到 stock_id 底下。
- **期貨交易日曆**:`futures_daily` 裡(任一契約)出現過的 `date` 集合。不用 `daily_prices`
  的日曆,原因見 R1。
- **當日一般量** `V(c, t)`:契約 c 在日期 t、`session = '一般'`、`contract_month NOT LIKE '%/%'`
  (價差組合列排除,與 `json_export._futures_by_stock` 同一條件)的 `SUM(volume)`。
  該日該契約沒有任何一般時段列 → `V` **不存在**(不是 0;見 R1)。
- **比較日** `W(c, t)`:t 之前(不含 t)最近的 **60 個**期貨交易日,**跳過 R4 排除日**
  (排除日不算在 60 裡,窗口往前延伸補足)。60 是 `json_export.py:221` 與 commit 訊息
  多次引用的同一個 60,不另立數字。
- **口**:volume 的單位;**股當量** = 口 × 契約乘數(股/口)。

## 1. 統計量:一般時段成交量創 60 個比較日新高

**旗標**:`flag(c, t) = V(c, t) > max{ V(c, d) : d ∈ W(c, t) }`(嚴格大於)。

**隨旗標一起輸出的事實(全部是整數口數,沒有比率、均值、名次、分數、z)**:

| 欄位 | 內容 |
|---|---|
| `today` | `V(c, t)` |
| `window_max` | `max V` over `W(c, t)` |
| `window_median` | `median V` over `W(c, t)`(60 個值的中位數,取下中位數,仍為整數) |
| `oi_change` | 當日總未平倉 − 前一個期貨交易日總未平倉(一般時段、非價差列、跨到期月相加;任一邊為 NULL 則此欄省略) |
| `window_days` | 恆為 60(寫出來是為了讓讀者知道比較基準的長度) |

使用者看到的是「今天 320 口、前 60 日最高 140 口、中位數 45 口、未平倉 +210 口」,
除法由人做。這滿足 `project-context.md` 原則 3(觸發理由要人看得懂),而且
`test_futures_export.test_payload_cannot_silently_gain_a_rate` 的 `RATIO_ISH` 閘門**維持原樣**——
這個切片不需要任何被閘門擋住的鍵。

**為什麼是「新高」而不是其他四個候選**:

| 候選 | 為何不採 |
|---|---|
| 今日 / 均值 | 均值被窗口內任何一次舊尖峰與轉倉日拉高,基準本身不穩;且是比率。 |
| 今日 / 中位數 | 中位數 2 口的契約,6 口就是 3 倍——**正是本專案多次踩到的小分母陷阱**。 |
| MAD z 值 | 薄契約的日量離散、零膨脹,MAD 常為 0,z 變無限大;不是理論缺陷,是實作上必然遇到的失敗。 |
| 「比之前平均多」照字面(比率 > 1) | 一半的日子都會被列出來,不是「異常」。 |
| **60 日新高(採用)** | 無分母、無分布假設、契約大小不變量(同一契約自比)、與本專案早已選定的「N 日新高」替代型態辨識(`project-context.md` 取捨 4)同一個習慣用語;chance rate 在獨立同分布下約 1/61 ≈ 1.6%,320 檔契約每晚約 5 檔是雜訊底線,名單短到能逐檔看。 |

**已知代價,事前承認**:一段持續放量的行情,只在「又創新高」的那一天上榜,第二天若量略低就不上榜。
這與現有的 N 日新高突破訊號行為一致;要追蹤已上榜的股票用自選追蹤,不靠放寬旗標。
**「改成前 3 名 / 20 日新高」不是 v1 允許的補救**(見 §3.5)。

## 2. 否決條件(per 契約-日;命中任一條 → 該契約該日不產生旗標,也不進入 §3 的檢定樣本)

### R1 歷史不足或有缺口(數的是「有列的日子」,不是比率)

- `W(c, t)` 必須能湊滿 **60 個**期貨交易日,且契約 c 在**每一個**比較日都有一般時段非價差列
  (`V` 存在)。少一天就否決。
- **缺列 ≠ 0 口**。TAIFEX 對掛牌中的契約每日都出列(量可為 0);沒有列代表「未掛牌 / 未公布 /
  匯入失敗」,三者都不是「沒人交易」。這條與 `providers/taifex.py` 模組說明的缺值原則同源。
- 日曆用**期貨交易日曆**而非 `daily_prices`:整市場某天匯入失敗時,那天在期貨日曆上根本不存在,
  窗口自然往前多取一天,不會把全部 320 檔契約一起否決 60 天;而**單一契約**缺某天(新掛牌、下市、
  暫停)才是有意義的缺口,依本條否決。修補整市場缺日的方法是重跑回補,不是放寬本條。

### R2 基準太薄(兩段,把「門檻」變成算術,不留一個事後可調的口數)

- **R2a 基準存在**:`window_median > 0`。中位數為 0 = 窗口內超過一半的日子沒有成交,
  這種契約沒有「日常」可比。這條沒有數字。
- **R2b 實質性**(把「3 倍的 2 口是 6 口」擋掉的那條):

  `100 × (today − window_median) × multiplier(c) ≥ spot_median_shares(s, t)`

  其中 `multiplier(c)` 是契約乘數(股/口),`spot_median_shares(s, t)` 是標的股 s 在
  **同一組比較日** `W(c, t)` 上 `daily_prices.volume`(單位:股)的中位數。
  白話:**超出中位數的那部分期貨量,換成股數,至少要等於現貨日常量的 1%**。
  - `1%` 不是從期貨資料挑的,是 `docs/04` §2 分點規則裡「淨買超 ≥ 成交值 1%」這條**已存在的**實質性
    門檻,同一個「什麼叫動了真錢」的尺。它是本專案裡唯一有先例可循、又與資料無關的來源。
  - 這裡出現了一個分母(現貨中位量),但它**不是統計量,是實質性閘門**,而且分母**結構上不會小**:
    能成為個股期貨標的的股票有流動性門檻,現貨 60 日中位量不會是幾張。寫成上面那條整數不等式,
    程式裡不需要任何浮點比率。
  - `multiplier(c)` 目前**沒有存**(`futures_contracts` 沒有這個欄位;schema.py:453 只在註解裡記了
    2,000/100 的事實;ETF 期貨的乘數又不同)。**乘數未知 → 否決**,三態原則不例外:不知道不等於
    2,000。這是本切片的前置實作項目(§4)。
  - `W(c, t)` 中任一天標的股沒有 `daily_prices` 列 → 沒有尺 → 否決。

### R3 時段:統計量**永遠**只用一般時段

不是「缺時段時退回一般對一般」,是**根本不用盤後**。理由:(1) 21:20 那輪常只有一般時段,
若旗標依賴盤後,同一天在 21:20 與次日會得到不同答案;(2) 混合時段的基準與單一時段的今日
是拿不同東西相比。盤後量若有列,照現行 export 以 `session_volume` 當事實輸出,**不參與**旗標、
比較窗口、R2、§3 任何一處。至於個股期貨盤後究竟有沒有列,是回補會揭露的事實,不改變本條。

### R4 機械性轉倉:結算日與其前 3 個市場日,排除於候選與比較窗口之外

- **結算日**:該月第三個星期三;若非市場日(以 `daily_prices` 任一列存在的日期為市場日),
  順延至次一市場日(TAIFEX 規則)。**每個月都有結算日**,不只季月。
- **排除日** = 結算日本身 + 其前 **3 個市場日**(正常週是週五、週一、週二 + 週三)。
  每月約 4/21 個交易日不可上榜,也**不進入任何契約的 `W`**(窗口跳過它們往前補)。
  兩邊一起排除是為了對稱:轉倉日進了窗口會把 `window_max` 抬高,讓真異常更難上榜——那是
  保守方向的偏誤,但仍是偏誤,一併排掉。
- **為何是日曆規則而不是「前月份量佔比位移超過 X」**:後者是一個比率,要一個 X,而 X 只能看資料挑。
  日曆規則不需要看任何資料。
- **為何是 3 天**:轉倉集中在最後幾個交易日;取 3 是在「排太少漏掉轉倉高峰」與「每月排掉四分之一
  交易日」之間的一個**事前**取捨。這個數字是選擇,不是推導;它的正當性只在於它現在就定下來,
  之後不動。
- **結算次日不排除**。新前月首日的量若真的創新高,由 `oi_change` 這個事實讓讀者自己分辨是
  重建部位還是新資金——`oi_change` 只**輸出**,不作為否決或旗標條件(用它當條件等於改掉使用者
  要的統計量)。
- 價差組合列(`'202609/202610'`)的排除維持現狀;本條處理的是價差列擋不住的、以兩腳單獨成交的轉倉。

### R5 契約身分改變

- 標的股減資、分割、合併時 TAIFEX 會調整契約;若以**新代碼**上市,它是新契約,R1 自動否決 60 天,
  不需額外處理。
- 若**同代碼但乘數變更**,窗口內前後的口數不可比。目前偵測不到(乘數未存),**記為已知盲點**:
  乘數欄位落地後,乘數在 `W(c, t) ∪ {t}` 內有變化 → 否決。

## 3. 全案否決(kill):過不了就整個功能不上線,不是「上線但加註」

這一節與 §2 是**不同種類**的規則——§2 決定某一天要不要輸出,§3 決定這個功能要不要存在——
但它**必須**寫在同一次 commit 裡:事前登記的效力只來自「在看到資料之前寫下」,分開決定就是
事後決定。先例:`docs/04` §2 事後 20 日分位在 n=18、1.81σ 下未過,整個往後看方向未進任何匯出。

### 3.1 樣本

- **評估期**:回補完成後 `futures_daily` 的全部日期,直到 battery 執行日 `as_of`。
- **成熟性**:t 之後必須有 ≥ 5 個現貨交易日(`daily_prices` 該股的日期)在 `as_of` 之前,
  否則 t **不進分母、也不算未命中**(同 `docs/STATUS.md` 往後看窗口成熟性的處理)。
- **F**:所有通過 §1 + §2 的旗標契約-日 (c, t)。
- **S(s, t)**:現貨對照旗標——同一條規則搬到現貨:`daily_prices.volume(s, t)` 嚴格大於該股
  之前最近 60 個現貨交易日的最大值(現貨不轉倉,**不套 R4**;現貨窗口以現貨日曆計)。
- **F_only** = { (c, t) ∈ F : ¬S(s(c), t) }——期貨創高而現貨當天**沒有**創高的日子。
  這才是「期貨量告訴你現貨量沒告訴你的事」的集合;使用者個股頁本來就有現貨量。

### 3.2 檢定 A:區辨性(純計數)

`|F_only| ≥ LOW_SAMPLE_SURVIVORS (= 30,沿用 branch_window_direction_battery.py:126)`。

不足時分兩種紀錄,**兩種都不上線**,但寫法不同:
- `|F| ≥ 30` 而 `|F_only| < 30`:**冗餘**。期貨創高幾乎都是現貨創高的回聲,功能沒有獨立內容。
  這是一個結論,要寫進 STATUS 告訴使用者。
- `|F| < 30`:**檢定力不足的無結果**,不是否證。等新交易日累積後依 §3.5 重跑。

### 3.3 檢定 B:資訊性(唯一的主要往後看量)

**假設**:期貨量先於現貨量——這是使用者「拿來做技術分析成交量的依據」唯一能成立的機制。

- **往後看量(唯一、事前定死)**:`hit(s, t) = 1` 若在 t 之後的 **5 個現貨交易日** {t+1..t+5}
  之內,任一天 `S(s, t') = 1`(現貨量創其 60 日新高)。二元、計數、與旗標同一條規則。
  **不用**往後報酬:那會替一個描述性功能背書一個使用者沒要求的預測宣稱。
- **旗標臂**:F_only 全部成熟成員,`n = |F_only|`,`h_F = Σ hit`。
- **安慰劑臂**:對每一檔在 F_only 有 k 筆的股票,從該股的**合格日**中不放回抽 k 天:合格日 =
  成熟、規則當天**有看過但沒有舉旗**(R1–R5 全部通過而 `flag = 0`)、¬S、且**不落在該股任一
  F 日之後 5 個現貨交易日內**(避免共用往後窗口)。抽樣種子 **固定為 0..9 共 10 組**。
  `h_P(seed)` = 安慰劑命中數。
- **判準**:令 `p̂ = h_P / n`,`σ_P = max(1, sqrt(n · p̂ · (1 − p̂)))`。
  每一組 seed 都必須滿足 `h_F − h_P(seed) ≥ 2 · σ_P`。**任一 seed 不過即不過**——
  「換 seed 直到過關」是 seed 參數要暴露的失敗模式(`docs/STATUS.md` 2026-09-08 條)。
- 形式沿用 `forward_vs_flow_matched_placebo`(2σ、多 seed、每 seed 皆過)。

### 3.4 裁決與紀錄

- A 過且 B 過 → **上線**(§4)。
- A 過、B 不過 → **不上線**。數字留在 battery JSON,不進資料表、匯出、面板。
- A 不過 → 依 §3.2 記冗餘或無結果;**不上線**。
- 每次執行都寫入 `docs/STATUS.md`:本文件 commit hash、回補完成時 `futures_daily` 的日期數與列數、
  `as_of`、`|F|`、`|F_only|`、每個 seed 的 `h_F / h_P / σ_P`、裁決、第幾次執行。

### 3.5 不允許的補救(在看到資料之後)

- 改 60、改 3 天、改 1%、改 2σ、改 30、改 5 天、改 seed 清單、改主要往後看量。
- 把「60 日新高」換成「前 3 名」「20 日新高」「今日 / 中位數 ≥ X」——那是 v2,只能用 v2 之後的交易日。
- 用往後報酬、波動、或任何**第二個**往後看量「補救」B。允許做探索,允許寫進 STATUS,**不允許改變裁決**。
- **重跑頻率**:無結果時,累積 ≥ 60 個新的期貨交易日才可重跑一次;每次重跑都要記次數。

## 4. 執行順序(執行者照這個順序做,每步之間不看資料)

1. Commit 本文件,把 hash 記進 `docs/STATUS.md`。**在此之前不對 `futures_daily` 下任何 SELECT。**
2. 回補完成;只記錄日期數與列數(這兩個數不是 §1–§3 任何門檻的輸入)。
3. 前置實作(可與回補平行,不需看資料):
   - `futures_contracts.contract_multiplier`(Integer, nullable;NULL = 未知)與其來源
     (TAIFEX 契約規格,標準型 2,000 / 小型 100 / ETF 另計);
   - 結算日曆函式(第三個星期三 + 市場日順延)與其單元測試(用固定日期,不用 DB);
   - `compute/futures_volume_battery.py`:依 §1–§3 計算,輸出 JSON,**不寫任何資料表**,
     風格同 `branch_window_direction_battery.py`。
4. 跑 battery 一次,把 §3.4 的紀錄寫入 STATUS。
5. 只有在 PASS 之後:實作 export 切片。它會在 per-stock `futures.contracts[].anomaly` 之下加
   §1 表格那五個整數鍵;`test_payload_cannot_silently_gain_a_rate` **不需修改**(沒有新增被擋的鍵),
   但要新增一個測試鎖住「這五個鍵都是整數、沒有第六個」。觸發理由與風險提醒範本:
   > 「{code} 期貨一般時段成交 {today} 口,創 60 個比較日新高(前高 {window_max} 口、中位數
   > {window_median} 口),未平倉較前日 {oi_change:+} 口。」
   > 「量創高不代表方向;結算週已排除;盤後未計;現貨當日{有/無}同步創高。」

## 5. 明確不做的事(v1)

- 不做跨契約排序(「今天誰最異常」)。旗標是二元的;名單順序用 `today − window_max`(整數口差)
  由前端排即可,不輸出名次。
- 不用未平倉當條件(它是存量,盤後為 NULL,且拿它當條件就不是使用者要的統計量)。
- 不對指數期貨、非個股商品套用本文件(`futures_contracts` 沒有的代碼一律不進計算)。

> 是因為它寫在「沒有人查詢過回補資料」的時候。撰寫本節時,250 交易日回補**仍然沒有執行**
> (`futures_daily` 依舊是 1,969 列、只有 2026-09-15 一天),撰寫者與執行者都沒有對回補資料
> 下過任何查詢,前置實作的測試全部用發明出來的 fixture。因此本節與 v1 一起凍結,不是
> 「看過資料之後的放寬」——這一節上 commit 之後,規則才是真的定死了。
>
> 本節**沒有更動任何一個事前登記的數字**:60、3 天、1%、2σ、30、5 天、seed 清單、主要往後看量
> 全部原封不動。改的是「某一條規則套在哪些日子上」與「哪一種結論算數」,以及三處把口頭約定
> 寫進文件。§3.5 的禁止清單因此完整成立。

### 6.1 修訂 1:R2b 的不等式是**候選日的篩子**,不是安慰劑資格的閘門

**規則**:

- **安慰劑合格日** = 成熟 ∧ R1 過 ∧ R2a 過 ∧ 乘數已知 ∧ `W` 上現貨窗口完整 ∧ 不在 R4 排除日 ∧
  `today ≤ window_max`(即 `flag = 0`)∧ `S(s, t)` **已知為假** ∧ 不落在該股任一 F 日的共用往後窗口。
- **R2b 的實質性不等式只在 `today > window_max` 那一天評估**。創高卻過不了實質性的日子以
  `R2b_immaterial` 否決,依 §2 標頭,它**兩臂都不進**(不上榜,也不進 §3 樣本)。
- R2b 的**前置條件**(乘數已知、`W` 上現貨窗口完整)留在原位,仍然閘住每一個契約-日:
  那兩件事描述的是「這一天的脈絡讀不讀得出來」,與當天量大不大無關。

**為什麼**(這是本次修訂唯一影響裁決的一條):

1. **它換掉了假設,不是收緊了假設。** §3.3 的假設是「期貨量先於現貨量」,訊號的對照是
   **沒有訊號**,也就是平常的日子。把實質性套在每一天,平靜日的 `today − window_median ≤ 0`
   使不等式結構上不可能成立,安慰劑池只剩下「高但沒破紀錄」的日子。拿創高日去比近似創高日,
   檢定的是「破紀錄 vs 接近破紀錄」——那是另一個假設。「比較嚴格」不是辯護,嚴格與否只在
   同一個假設之內才有意義。
2. **它在機械上自我毀滅,而且不會被時間治好。** 一檔薄契約(窗口中位數 3 口,對上 5,000,000 股的
   現貨日常量)幾乎沒有一個平靜日跨得過實質性,但它自己真正的新高輕鬆跨過。池子恰恰在
   會舉旗的地方餓死:只要有一檔薄契約舉了兩次旗而池子只有一天,§3.3 的計數配對就抽不滿,
   整個檢定 B 變成「不可評估」。這不是資料不夠,是規則自己造成的,再多交易日也補不回來,
   §3.5 的重跑規則救不了它。
3. **成本已經寫出來了。** 池子變大之後,安慰劑臂會納入真正平凡的日子,`h_P` 只會更誠實;
   若 `h_F − h_P` 因此縮小到過不了 2σ,那就是檢定該給的答案。

**程式**:`evaluate_contract_day` 把不等式移到 `today > window_max` 之後;
`refusals.R2b_immaterial` 的意思隨之變成「**創高日**被實質性擋下來的次數」。

### 6.2 修訂 2:成熟 = 往後五天的 `S` **五個都算得出來**

**規則**:t 成熟的條件是 t 之後有 5 個現貨交易日,**而且 `S(s, t+1..t+5)` 五個全部已知**。
任一個是「不知道」→ t 從旗標臂、安慰劑臂、安慰劑池**三處一起**排除。

**為什麼**:§3.1 寫的是不可評分的日子「不進分母、**也不算未命中**」。舊實作只數「有沒有 5 天」,
於是窗口裡 `S` 為 `None` 的日子照樣進分母,而 `forward_hit` 把 `None` 讀成「沒有創高」——
後半句被違反了。未知讀成未命中會壓低 `h_F` 與 `h_P` 兩邊,但兩邊的未知密度沒有理由相同,
所以偏誤的方向不確定;不確定方向的偏誤比保守偏誤更糟。

### 6.3 修訂 3:成熟性同樣管檢定 A(確認既有行為,把理由記下來)

**規則**:檢定 A 數的是 F 與 F_only 的**成熟**成員,A 與 B 用同一個樣本定義。

**為什麼**:§3.1 是「樣本」這一節,它管的是整個 §3;而 §3.3 寫 `n = |F_only|`,這個寫法只有在
F_only 本來就只含成熟成員時才說得通。兩個檢定用兩種樣本定義,會出現「A 過是靠不成熟的日子」
這種讀不出意思的結果。`sets.f_all_including_immature` 與 `sets.f_immature` 照舊輸出,
所以「成熟性砍掉了多少」是看得見的,不是藏起來的。

**程式**:既有行為已正確,本次未改;此處只是把理由寫進文件,並用測試鎖住。

### 6.4 修訂 4:「冗餘」不得經由 `S` 未知的日子成立

**規則**:檢定 A 的冗餘結局,條件改記為 `|F_only| + |F_{S=1}| ≥ 30` 且 `|F_only| < 30`。
若 `|F|` 是靠 `S` 不知道的日子才湊到 30,結局是**檢定力不足的無結果**,不是冗餘。

**為什麼**:「冗餘」是一個**結論**,會寫進 `docs/STATUS.md` 告訴使用者「期貨創高幾乎都是現貨
創高的回聲,這個功能沒有獨立內容」。那句話只關於 `S = 1` 的日子。`S` 未知的日子對它一個字
都沒說,拿它們撐起一個結論,等於用「讀不到」去證明「是回聲」。無結果與冗餘的差別不是程度
差別:前者依 §3.5 可以重跑,後者是收案。

### 6.5 修訂 5:三條既有行為,確認並記錄

- **旗標日自己**留在安慰劑池之外。§3.3 的「之後 5 個交易日」規則存在的理由是避免共用往後窗口,
  而 F 日與旗標臂共用的是**整個**窗口。§0 點名的雙契約情形(1565 的 MYF/OMF)正是這條會咬到的
  地方:同一天一個契約舉旗、另一個沒舉,抽到後者就等於拿旗標臂的同一個觀測當對照。
- **安慰劑抽不滿 → 不可評估**,不是給一個分數。兩點澄清:
  (i) 不可評估 = **不上線**,而且對 §3.5 的重跑規則算**無結果**(檢定從來沒有被評分,沒有東西可以
  被否證);(ii) JSON 必須逐檔列出抽不滿的 `(stock_id, k, pool_size)`。差額與 seed 無關(每個 seed
  都抽 `min(k, |pool|)` 天),而讀者必須分得出「這檔結構性餓死」與「再等幾個月就補得滿」——
  一個總數辦不到這件事。這是**報告義務,不是規則**,它不改變任何裁決。
- **`S` 未知的旗標日不進 F_only**。未知 ≠ 否;F_only 要的是一個**已確立的**否定。

### 6.6 修訂 6:三處澄清(寫下來,免得日後被「發現」)

- **中位數慣例**:`spot_median_shares` 取**下中位數**,與 `window_median` 同一個慣例、同一個理由
  (整數,不生浮點)。方向是六十個裡的一個名次,偏向**較容易**通過 R2b。現在記下來,
  它就不會在看到資料之後變成一個「可以調的地方」。
- **F 日**之前**的日子刻意不排除**。t−1 的安慰劑與 t 的 F 共用四個往後日,這個滲漏讓 `h_P` 跟著
  `h_F` 走,方向是**更難過關**。它事前登記成一個「不可用來補救」的已知滲漏:檢定 B 失敗之後,
  「池子被 F 前日汙染了」不能拿來當重做的理由。
- **`as_of` 的定義**:期貨與現貨**都已匯入**的最後一天;成熟性數的是 `≤ as_of` 的現貨交易日。
  §3.1 的字面是「在 as_of 之前」,程式數的是 `≤ as_of`,兩者只差 as_of 當天算不算那 5 天之一;
  這裡把它定死,而不是留一個文字與程式的落差等人去解釋。

> 一旦有人拿它去改「什麼算一個異常」,那就是 v2,依 §3.5 只能用 v2 之後的交易日重新取得資格。

### 7.1 `oi_change` 被省略時,句子在括號後面結束

理由:缺值就是缺值,沒有子句。寫 `+0` 是把「不知道」講成「一口都沒變」;寫「未平倉未公布」
是從 R1 講明的三個不可分辨的成因(未掛牌 / 未公布 / 匯入失敗)裡挑一個當答案。
一個缺掉的欄位沒有資格擁有一句話。

### 7.2 現貨旗標未知時,風險那句在「盤後未計。」結束

理由同 7.1:「有同步創高」與「無同步創高」都是**正面主張**,不知道的時候兩個都不該拿。
也不另造第三種措辭——那只是把 7.1 拒絕的事換一個地方做。
(實測:1,052 個旗標日裡 `spot_flag_unknown = 0`,所以這條目前一次都沒觸發;它存在是為了
那個「目前」有一天不成立的時候。)

### 7.3 兩段文字掛在契約上,鍵是 `reasons` / `risks`,條目形狀 `{code, text}`

位置:`futures.contracts[].anomaly` 旁邊,與旗標同生共死(沒有 `anomaly` 就沒有這兩個鍵)。
形狀就是既有的 `ReasonItem`,只是它兩個選填欄位都不給:`web/lib/types.ts` 已經把
`points?` 與 `value?` 宣告成選填,而 payload 裡 `raw_reasons` 與 `technical.reasons` /
`technical.risks` 本來就是這個形狀,所以這裡不發明新型別。

- **不給 `points`**:這個旗標不進任何分數。在一個**可排序的欄位**裡放一個數字,等於偷偷
  建立一個跨契約名次,而 §5 明文不做。
- **不給 `value`**:那五個事實已經在 `anomaly` 裡,重複一次就會有兩個可以各自漂移的真相。
- **代碼定死**:`F1_FUTURES_VOLUME_60D_HIGH`、`R_FUTURES_VOLUME_NO_DIRECTION`。

### 7.4 `anomaly` 是**四個或五個**鍵,不是固定五個

`oi_change` 依 §1 表格本來就是選填的(任一邊為 NULL 就整個省略,見 7.1)。鎖住的是
「**五個之中的一個子集,絕不出現第六個,而且全部是整數**」,不是「一定五個」。
前端把它型別成 `oi_change?: number`,缺鍵時**整列不顯示**,不是印 0、也不是印一個破折號。

### 7.5 市場層級的名單:`radar.json` 的 `futures_volume_anomalies`

§1 說「名單短到能逐檔看」、§5 說「名單順序用 `today − window_max` 由前端排」,兩句話都預設
存在一份**市場層級**的名單;步驟 5 只把旗標掛到 `stocks/{id}.json` 上,那份名單當時做不出來。
本節把它補上。

- **產出來源**:與個股區塊**同一次** `futures_volume_anomalies` 呼叫的結果重新排列而已。
  整個 export 只評估規則一次——第二趟就是第二條規則,那正是這份文件存在的理由。
- **條目形狀**:`{stock_id, code, anomaly, reasons, risks}`,後三個**原封不動**沿用個股區塊的
  結構,不做攤平變體。
- **順序**:`today − window_max` 由大到小,同分用 `code` 由小到大(後者只為了檔案可重現)。
  這是**順序,不是名次**:不輸出 `rank` / `position` / `score` 之類的鍵,§5 不做跨契約排序。
- **三態**(與 `futures` 鍵同一個約定,不可塌成兩態):
  - **沒有這個鍵** = 今天**沒有算過**(例:期貨資料還沒跟上 export 日,見 7.8)。沒有主張。
  - **有鍵、空陣列** = 算過了,今天沒有契約舉旗。這是一個**有日期的正面主張**。
  - **有鍵、非空** = 今天舉旗的契約。
  把前兩者塌成同一種表示,就是重犯 `futures` 鍵三態本來要擋的那個錯。
- **不依股票去重**:單位是契約。1565 的 `MYF`(2,000)與 `OMF`(100)可以同一天都舉旗,
  去重會無聲吞掉其中一個。

### 7.6 `daily.volume` 與 `anomaly.today` 是兩個不同的數字

`daily.volume` 是**一般 + 盤後**兩個時段的和(`session_volume` 同時列出各時段);
`anomaly.today` 依 R3 **只有一般時段**。兩者永遠不可以當成同一個數字顯示。
排序鍵是 `anomaly.today − anomaly.window_max`,**不是**任何由 `daily.volume` 導出的東西。

### 7.7 沒有 `anomaly` 有三種意思,而且刻意不可分辨

(a) 被 §2 否決(R1/R2a/R2b/R4);(b) 規則看過了但沒創高;(c) 期貨還沒匯進來。
三者都**不是一個異常**,所以輸出上不區分——這是 §2 標頭的既有約定,不是這裡新加的。
**UI 不得把其中任何一種標成「正常」**:那是一個沒人做過的主張。
若要一個「尚未公布」的狀態,它的依據是 `daily` 這個鍵的有無(那個鍵本身就是三態的),
不是 `anomaly` 的有無。

### 7.8 可見性窗口:t 日的旗標要到 t+1 的 21:2x 才看得見

`import-futures` 排在 **21:20**(`daily-margin.sh`),而餵源(`fetch_daily_report()`)**沒有
日期參數**,只給最新一份**完整**的日報。t 日 21:20 跑到那裡時,t 日自己的盤後時段還沒收
(約 t+1 的 05:00),所以那份最新的完整日報是 **t−1** 的。因此:

- **t 日 21:2x 那一版**,期貨資料日是 **t−1**,呈現的是 t−1 的旗標;
- **t 日的旗標**在 **t+1 的 21:2x** 那一輪才第一次出現,並在 **t+2 的 21:2x** 被換掉。

換句話說,期貨側**常態落後現貨一個交易日**,而且那份落後的資料是**完整的兩個時段**——
production 2026-09-18 是一般 1,763 列 + 盤後 39 列。

> **事後修正(二)**:本節前一版寫「t 日的旗標從 t 日 21:20 那一輪開始可見」,**是錯的**。
> 它把「21:20 匯入」讀成了「21:20 匯入當天」,而餵源根本不接受日期。錯誤的後果不只是
> 記錄不準:§7.5 第一態的文案照著它寫成「期貨還停在前一個交易日」,前端因此把一個**常態**
> 講成一個**暫時狀態**,而 export 也照著同一個誤解拿現貨日去問期貨(見 §7.12)。
> 這裡沿用前一次的作法:把錯的那一版留著、寫清楚錯在哪,而不是把它抹掉。
>
> **事後修正(一,保留)**:更早的初稿寫「從約 01:30 的夜間發佈開始可見」,那也是錯的——
> 它漏看了 `daily-margin.sh` 在 `import-futures` 之後自己就 export + deploy。

這整件事是**正確行為,不是 bug**:**不要**用「把昨天的區塊留著頂替今天」去「修」它——
那會讓面板上的日期與內容對不起來,正好是 §2 R3 不用盤後的同一個理由(同一天在兩個
時刻給出不同答案)。要修的是**把日期講出來**(§7.12),不是把資料搬到別的日子去。

### 7.9 藥丸顏色:`F1_…` 走中性,`R_…` 走風險

`ReasonPill.reasonFamily` 目前沒有 `F` 開頭的分支,所以 `F1_FUTURES_VOLUME_60D_HIGH`
落到 `neutral`,而 `R_FUTURES_VOLUME_NO_DIRECTION` 因為 `startsWith("R")` 落到 `risk`。
**兩個都是對的**:這是一個描述性的事實,不是一個技術面評分。記在這裡是為了擋下日後
「順手補一個 `F → tech` 分支」的修改——那會讓它看起來像一個它從來沒有的技術分數。

### 7.10 一檔股票可以有兩個契約,`window_days` 從區塊讀不要寫死

1565 的 `MYF`(2,000 股/口)與 `OMF`(100 股/口)是同一檔股票的兩個不同乘數契約,
同一天可以都舉旗(§0 點名過這個情形,§6.5 也咬到過)。**任何一層都不依股票去重。**
UI 顯示「60 個比較日」時讀 `anomaly.window_days`,不要在前端寫死 60——60 只能由 v2 更改,
而一個寫死的 60 會在那一天變成第二個、不受 §3.5 管束的真相。

### 7.11 空名單那一態也要講得出比較窗口:`futures_volume_anomalies_meta`

**地位同 §7 全節:資料可見之後寫的,只動呈現。** 它沒有新增、刪除或更動任何一條規則、
任何一個門檻、任何一個數字,也沒有改變任何一個契約-日會不會舉旗;整節刪掉重跑 battery,
`|F|`、`|F_only|`、`h_F`、`h_P`、裁決一個數字都不會變。

**逼出它的是 §7.10。** §7.5 的第二態(**有鍵、空陣列** = 算過了、今天沒有契約舉旗)是一個
有日期的正面主張,那句話該說的是「今日沒有契約創 **60** 個比較日新高」。但那一態裡
**一個 `anomaly` 區塊都沒有**,`window_days` 無處可讀;而 §7.10 明文禁止在前端寫死 60。
兩條規則一起把那句話變成寫不出來的——初版因此只能少講比較窗口,寫成
「已完成計算:今日沒有契約的一般時段成交量創新高。」。缺的不是文案,是 payload。

**形狀:平行的鍵,不是把名單包進物件。**

- `radar.json` 既有的習慣就是「清單 + 同名的隨附事實」兩個平行鍵(`strategies` 與
  `strategy_meta`)。這裡沿用:`futures_volume_anomalies_meta = {"window_days": 60}`。
- 更重要的理由是三態:§7.5 的「**沒有這個鍵**」必須是一個真的不存在的鍵。把陣列包進
  物件之後,「沒算過」與「算過但是空的」就得靠物件裡某個欄位去分辨,那正是 §7.5 點名
  不可以塌掉的那條界線。平行的鍵讓名單自己的三態**一個字都沒有動**。
- **兩個鍵同生共死**:meta 由名單導出(`anomaly_index_meta(index)`,`index is None → None`),
  所以結構上不可能出現一個沒有名單的孤兒 `window_days`。
- 數字取自 `futures_volume_battery.WINDOW_DAYS` 本人,不另寫一個字面的 60——§3.5 凍結了
  那個數字,第二份拷貝會無聲地漂走。測試把常數換成 7,輸出必須跟著變成 7。
- meta 只有 `window_days` 一個整數欄位。它**不是**名次或評分的落腳處:§5 不做跨契約排序,
  這個鍵裡永遠不會長出 `rank` / `score` / 比率。名單的順序與內容完全沒有改變。

**前端**:`futuresAnomalyMarketState` 的 `computed-empty` 多帶一個 `windowDays`,
句子由 `anomalyEmptyStateText` 這個純函式產出(放在 `lib/futures.ts` 而不是 JSX 裡,
是因為句子裡有一個數字,而寫在 JSX 裡沒有東西擋得住有人直接打一個 60)。空名單的文案是:

> 「{data_date} 已完成計算:今日沒有契約的一般時段成交量創 {window_days} 個比較日新高。」

`windowDays` 拿不到(payload 沒給 meta)時,**整段子句拿掉**,回到「…成交量創新高。」,
**不是**退回一個寫死的 60——同 §7.1 的習慣:缺值就是缺值,不編一個數字上去。
第一態(沒有算過)的文案完全未動,仍然不做任何主張。

(這句話的日期與「今日」二字後來由 §7.12 改寫:它講的是**期貨行情日**,不是 `data_date`。)

### 7.12 整個 `futures` 切片錨在期貨行情日,而且兩個 payload 都把那一天寫出來

**地位同 §7 全節:資料可見之後寫的,只動呈現與呈現用的日期。** 它沒有新增、刪除或更動任何
一條規則、任何一個門檻、任何一個數字;`flag(c, t)` 對每一個 `(c, t)` 的答案一個字都沒有變,
整節刪掉重跑 battery,`|F|`、`|F_only|`、`h_F`、`h_P`、裁決一個數字都不會變。**它不是 v2**:
改的是「頁面顯示哪一個 t」,而那件事 §1–§5 從頭到尾沒有規定過。

**被修的缺陷。** export 用 `data_date`(現貨日)去問期貨:

- `contracts[].daily` 的 `WHERE date = :d`,
- `futures_volume_anomalies(conn, d)` 裡的 `futures_days[-1] != as_of` → 回「沒有算過」。

而 §7.8 講清楚了,期貨資料日**常態就是** `現貨日 − 1 個交易日`。兩件事合起來:市場層級的
`futures_volume_anomalies` 鍵**從未出現過**,`contracts[].daily` **從未被填過**,而唯一能讓
那個閘門通過的日子是**現貨匯入失敗**的那一天。上線的不是「慢一天的功能」,是「只在故障日
才顯示的功能」。production 實測:`futures_daily` 最大 2026-09-18、`daily_prices` 最大
2026-09-21;09-21 的 21:20 匯入的是 09-18,09-18 匯入 09-17,09-17 匯入 09-16。

**規則不是新的。** §6.6 早就把 `as_of` 定義成「期貨與現貨**都已匯入**的最後一天」;違反那個
定義的是 export,這裡只是回去遵守它。`json_export` 本來就算好了那個值(`f_date =
latest("futures_daily")`),只是沒有把它交給切片。

**錨點:一個變數。** `f_date` 同時餵 `freshness.futures.date`、`_futures_by_stock` 的
`as_of`(於是 `daily`、`daily_as_of`、旗標全部同一天)、以及 meta 的 `as_of`。
第二個來源就是第二個可以漂走的真相。

**日期寫在哪裡(明講,不推導):**

- **市場層級**:`futures_volume_anomalies_meta.as_of`。與 `freshness.futures.date` 相等,
  測試鎖住這個等號。
- **個股**:`futures.daily_as_of`,`list_as_of` 的**兄弟鍵**。不叫裸的 `as_of`——旁邊就站著
  一個 `list_as_of`(標的清單刷新日),兩個 as_of 並排會讓讀的人以為是同一個東西的兩半。
  沒有任何期貨行情日時**整個鍵不輸出**(同 absent-key 慣例),不寫 `null`。
  `daily.date` 保留,而且測試鎖住 `daily.date == daily_as_of`。
- **為什麼不從別處推導**:§7.4 禁止 `anomaly` 長出第六個鍵;某一檔股票的契約可能當天
  沒有 `daily` 列,推無可推;而從 `daily` 推等於把兩句各自獨立的 SQL 偷偷綁在一起。

**UI 文案。** 規則三條:不用沒有限定的「今日 / 今天」;每一個**有主張**的狀態都要講出期貨
行情日;§4 步驟 5 的兩段範本**逐字不動**——日期放在標題,不進範本句子裡。也**不解釋原因**
(沒有人讀過 TAIFEX 的公布時刻表,只陳述日期,不陳述解釋)。

- 沒有算過:「尚未計算期貨成交量異常:這一版沒有可用的期貨行情日。這不代表沒有異常。」
  舊文案第二句(「期貨資料每日 21:20 匯入,這一版的期貨還停在前一個交易日」)**刪除**:
  它把常態講成暫時狀態,而且那個模型是錯的(§7.8)。
- 算過了、沒有人舉旗:「期貨 {as_of} 已完成計算:沒有契約的一般時段成交量創 {window_days}
  個比較日新高。」(`window_days` 缺席時照 §7.11 拿掉那個子句;`as_of` 缺席時拿掉日期,
  **不得**拿 `data_date` 頂替。)
- 有名單:「期貨 {as_of}:共 N 個契約舉旗。單位是契約……」(後半句原封不動)。
- **落差那一句**,兩個有主張的狀態都顯示,而且只在 `as_of !== data_date` 時顯示:
  「期貨行情日 {as_of};本頁其他資料為 {data_date}。」**絕不說「落後一天」**——前端沒有
  交易日曆,數不出兩個日期之間有幾個交易日,它只說得出那是哪兩天。
- 個股頁區塊標題:「期貨成交量異常({daily_as_of})」;事實列的標籤「今日一般時段」改成
  「一般時段成交」(那一天不是使用者的今天)。

**順帶修掉的兩件事(同一個誤解的另外兩個出口):**

1. `freshness.futures.stale` 原本是 `f_date != d`,於是**恆為真**,`summary_text` 每天承諾
   「個股期貨資料尚未更新,稍後自動補齊」——而這條管線**補不了**:餵源沒有日期參數,漏掉
   的那天只能由人跑 `backfill-futures`。改成 `f_date not in (d, prev)`(「連前一個交易日都
   沒跟上」才算舊;期貨反而追上現貨當然也不算舊),並把期貨**移出**那句「稍後自動補齊」,
   它的落後改由 freshness 徽章講(`web/app/page.tsx` 的 `FRESH_LABEL` 補上 `futures`,
   先前缺這一行,徽章會印出原始鍵)。
2. 幾處註解寫著「21:20 只看得到一般盤」(`json_export.py`、`vps/scripts/daily-margin.sh`)。
   production 打臉:2026-09-18 兩個時段都在(一般 1,763、盤後 39)。註解改掉。
   **R3 的凍結文字不動**——扛著 R3 的是它的理由 (2)(盤後與一般是不對等的比較),
   不是理由 (1)(公布時刻);理由 (1) 錯了,規則不受影響。

### 7.13 R4 在日曆邊緣:算不出結算日 ⇒ 不主張(這一條是正確性,不是呈現)

**地位同 §7 全節,但要說清楚它與其他條的差別**:它**確實會改變**某些 `(c, t)` 的輸出——
把「舉旗」變成「不主張」。它仍然不是 v2,因為 `flag(c, t)` 這條規則一個字都沒有改:R4 本來
就寫著「結算日與其前 3 個市場日不得上榜」,改的是 export 在**算不出結算日**時該怎麼辦。

**缺陷。** `settlement_date()` 在名目第三個星期三超出已知日曆時回 `None`(那是刻意的,
它拒絕外推),`settlement_exclusion_days()` 於是回一個空清單——而空清單在聯集裡與
「這個月沒有排除日」**看起來一模一樣**。battery 帶著事後日曆跑,任何候選日的下一個結算日
都已經在日曆裡,這個塌陷永遠不會發生;**export 永遠坐在日曆的尾巴上**,它會發生,而且
方向是**放行**:結算日前 1–3 個市場日可以上榜,而被檢定過的規則排除它們。上線的規則於是
在邊緣與被檢定過的規則不同——這不是呈現問題。

**裁決:不可判定 ⇒ 不主張。**「定位不到結算日」一律當成「不要輸出」,**絕不**當成
「沒有被排除」。整個 `futures_volume_anomalies` 回 `None`(§7.5 第一態,沒有主張),
不是 `{}`(那是一個有日期的正面主張)。

**「不可判定」怎麼判定**(`settlement_is_determinable`):

- 該月結算日落在已知日曆之內 → 答得出來,照 R4 判;
- 名目日還在已知日曆之後,但候選日與名目日之間至少有 `EXCLUSION_MARKET_DAYS_BEFORE`(3)
  個市場日 → 候選日不可能落在窗口裡,答得出來(而答案是「沒有被排除」);
- 否則 → 答不出來。

中間那一條是整條規則的難處,必須寫下來:**「定位不到結算日就一律不主張」是行不通的**。
export 的日曆永遠停在今天,而名目結算日在每個月的 15–21 日,所以那條「保守」規則會讓
每個月從 1 號到第三個星期三的**每一天**都停止主張——整整半個月的功能消失。那不是保守,
那是關掉。所以要數的是「離那個窗口有多遠」,而數的時候:已知日曆之內用真的市場日,
**已知日曆之後把每一個平日當成市場日**。

那個外推**可能錯**:候選日與結算日之間若整段連假,真正的市場日比平日少,一個該排除的
日子會被放行。但那個錯誤的方向與**修之前的行為完全相同**,所以這個函式在任何一天都不會
比現況更差,而在正常的日曆上它把真正的邊緣案例擋下來。用日曆日去近似不行(市場日數不
由日曆日數決定),用「整個月」去近似更糟(見上一段)。**這個外推是這一節唯一的取捨,
記在這裡就是為了它日後被人「發現」時,看得到它是被選的而不是被漏的。**

**日曆讀到哪一天**:市場日日曆讀到 `data_date`(現貨日),不是 `as_of`(期貨日)。R4 的窗口
是往未來看的,而現貨已經比期貨多一天——那一天是白拿的先見之明,不拿等於自找一個
不可判定。

### 7.14 每日事實上畫面;`daily` 多一個 `oi_change`,每一個契約-日都給

**地位同 §7 全節:資料可見之後寫的,只動呈現與呈現用的欄位。** 它沒有新增、刪除或更動
任何一條規則、任何一個門檻、任何一個數字(60 / 3 天 / 1% / 2σ / 30 / 5 天 / seed 0..9 /
主要往後看量全部原封不動),也沒有改變任何一個契約-日會不會舉旗。把本條整條刪掉重跑
battery,`|F|`、`|F_only|`、`h_F`、`h_P`、裁決一個數字都不會變。**它不是 v2**:
`anomaly` 區塊的五個鍵一個沒動,`ANOMALY_FACT_KEYS` 與 §7.4 的鎖完好。

**缺口。** 21:20 那一輪每天為約 320 個契約匯入日量、未平倉與時段拆分,`_futures_by_stock`
也照實寫進 `futures.contracts[].daily`——而 `web/` 裡沒有一個元件讀它:`session_volume` 與
`open_interest` 只在 `lib/types.ts` 的型別宣告裡出現過。於是典型的一天四個契約舉旗、拿到
一個區塊,其餘約 248 檔標的股只看得到「有個股期貨 CDF QFF」這個徽章,而我們手上有它們的
量與未平倉。

**兩件事:**

1. **個股頁多一塊每日事實**,對**每一個**帶 `daily` 的契約都畫(不只舉旗的):行情日、
   一般+盤後合計成交、各時段成交、未平倉、未平倉較前日。沒有 `daily` 的契約在這一塊裡
   **什麼都不畫**——不是「正常」,也不是「無交易」(§7.7 / R1:未掛牌 / 未公布 / 匯入失敗
   三者不可分辨)。標題的日期讀 `daily.date`,不讀 `data_date`。
2. **`daily.oi_change`**:未平倉較前一個期貨交易日的變化,對**每一個**契約-日輸出,
   不再只活在旗標裡。部位是在建還是在減,是這個切片唯一講得出方向的事實,而它與
   「今天量有沒有創高」無關;把它綁在旗標上等於一年 250 天只講四天。

**規則與數字的來源,一個不新造:**

- 「前一個期貨交易日」與缺值處理一律走 `futures_volume_battery.oi_change()` 本人
  (口徑同 §1 表格:一般時段、非價差列、跨到期月相加;任一邊為 NULL 則整個欄位省略)。
  export 在這裡自己再數一次「昨天」,就會有第二個與 `anomaly.oi_change` **同名**、可以各自
  漂走的數字——而舉旗的契約上那兩個數字會並排顯示。測試鎖住兩者逐字相同,也鎖住
  `json_export.oi_change is futures_volume_battery.oi_change`。
- `daily.open_interest` 的加總不篩時段,但盤後列的未平倉來源就是 `'-'`(NULL),所以它與
  上面那個一般時段口徑在資料上是同一個數。未平倉是**存量不是流量**:時段拆分只適用於
  成交量,未平倉那兩列的標籤因此不帶任何時段字樣。

**呈現的三條,與 §7.1 / §7.6 / §7.7 同源:**

- **`daily.volume` 與 `anomaly.today` 是兩個數字**(§7.6),而且它們現在真的會並排出現在
  同一頁上。分辨它們的只有標籤,所以合計那一列叫「一般+盤後合計成交」而不是「成交量」
  ——後者擋不住誤讀。異常區塊那一列維持「一般時段成交」,兩邊的文字都被測試鎖住。
- **`oi_change` 缺席 = 整列不顯示**(§7.1):不是 0、不是破折號、不是「未公布」。而真正的
  `0`(「一口都沒變」)**必須顯示成 0**。這兩件事在畫面上長得一樣,分辨它們的只有那一列
  在不在——與 §7.1 點名的是同一個陷阱,只是換到 `daily` 底下再出現一次。
- **不算比率**:合計與各時段、未平倉與其日變化全部是 payload 裡的整數,前端不做除法、
  不做差值、不給名次。`test_payload_cannot_silently_gain_a_rate` 未修改;前端那一條由
  `futures.test.ts` 逐列比對「每個顯示值都是 payload 裡原本那個整數」把守。

### 7.15 未平倉:水位只讀一般時段;缺席講得出口;市場層級的方向計數

**地位同 §7 全節:資料可見之後寫的。** 前兩條只動呈現與呈現用的欄位;第三條**新增一個
市場層級的鍵**,而那個鍵**不是一個訊號**(理由見下,那是本條最重要的一段)。三條都沒有
新增、刪除或更動任何一條規則、任何一個門檻、任何一個數字(60 / 3 天 / 1% / 2σ / 30 /
5 天 / seed 0..9 / 主要往後看量全部原封不動),也沒有改變任何一個契約-日會不會舉旗。
把本條整條刪掉重跑 battery,`|F|`、`|F_only|`、`h_F`、`h_P`、裁決一個數字都不會變。
`anomaly` 的五個鍵、`ANOMALY_FACT_KEYS`、§7.4 與 §7.11 的鎖全部完好。

#### (一)`daily.open_interest` 取一般時段,不是跨時段相加(這是正確性)

§7.14 寫著「`daily.open_interest` 的加總不篩時段,但盤後列的未平倉來源就是 `'-'`(NULL),
所以它與一般時段口徑在資料上是同一個數」。那句話**今天為真,而它為真的理由是錯的**:
它是一個關於**來源今天長什麼樣子**的觀察,不是一個關於未平倉是什麼的理由。

未平倉是**存量不是流量**(§7.14 自己就是這樣寫的)。同一天兩個時段的水位相加沒有意義,
即使相加的結果今天恰好正確。而 `oi_change` 依 §1 表格**本來就只讀一般時段**,於是兩者
的口徑靠一個外部事實才對得上:TAIFEX 哪天開始對盤後給未平倉,水位會無聲地翻倍,日變化
仍然是對的,**同一張卡片上的兩個數字會互相矛盾**,而且沒有一個測試會紅。

改成一般時段(走 `load_regular_session_volumes` 那一句 SQL 本人,與 `oi_change` 同源),
對今天的資料是 no-op,而且永遠正確。測試反事實地給盤後列一個未平倉數字,鎖住水位一動
也不動(`test_the_after_hours_session_does_not_reach_the_open_interest_level`),另一個
鎖住水位與日變化同生共死。**R3 因此名副其實**:這個切片裡再也沒有任何一個數字跨時段。

#### (二)沒有 `daily` 的契約:把缺席講成缺席,一句,不解釋

§7.14 讓沒有 `daily` 的契約在畫面上**什麼都不畫**,理由是缺席有未掛牌 / 未公布 /
匯入失敗三種不可分辨的成因(R1)。理由是對的,但結果有一個沒被看見的後果:**「什麼都
沒有」與「這個功能還沒上線」長得一模一樣**。

§7.7 早就寫好了出路:「若要一個『尚未公布』的狀態,它的依據是 `daily` 這個鍵的有無
(那個鍵本身就是三態的),不是 `anomaly` 的有無。」所以個股頁對這種契約畫一行:

> 「{code} 在 {daily_as_of} 沒有列。」

這句話**只陳述缺席,不解釋缺席**。不寫「未公布 / 未上市 / 匯入失敗」——挑一個講就是替
資料做了一個它支持不了的選擇,與 §7.1 拒絕「未平倉未公布」是同一條理由。也不寫「正常」
或「無交易」(§7.7 明文禁止)。日期是期貨行情日;拿不到那一天時整句話不存在,因為
「沒有列」一定要說得出是哪一天沒有列。前端由 `noDailyRowText` 一個純函式產出,測試逐字
鎖住,並鎖住那六個被禁的詞一個都沒出現。

#### (三)市場層級的未平倉方向計數 `futures_open_interest_direction`

**缺口**:市場頁只有旗標名單,而旗標是少數(典型一天個位數,空名單是常態)。沒有任何
一個地方回答「今天全市場的部位是在建還是在減」——而那正是這個功能存在的那個問題的
市場層級形式。約 320 個契約每天都有這個事實,一個都沒有被聚合過。

**形狀**:`{as_of, increased, decreased, unchanged, undetermined}`。四個計數,涵蓋
**全部**契約(不只有 `daily` 的那些),和恆等於契約總數。

**為什麼它不需要 battery,而 §1 的旗標需要——這一段是本條存在的全部條件,日後想在
這裡加一個門檻的人必須先讀到它:**

- §1 的旗標做的是一個**資訊性**主張:「這個旗標**告訴你**一些事」(使用者原話是「拿來
  做判斷籌碼或是技術分析成交量的依據」)。一個「告訴你某件事」的宣稱可以被否證,所以
  §3 要求它先被否證看看——區辨性、安慰劑、2σ、十組 seed,過不了就整個不上線。
- 這四個計數做的是一個**描述性**陳述:「今天有 N 個契約的未平倉比前一個期貨交易日高」。
  它**沒有**主張這件事之後會發生什麼,也沒有主張今天算不算不尋常。沒有主張就沒有虛無
  假設,沒有虛無假設就沒有東西可以被否證。一份 battery 對它而言不是「更嚴謹」,是
  **無從執行**。

**這個豁免只在它保持描述性的時候成立。** 以下任何一項都會讓它變成一個穿著本功能外衣、
卻從來沒有被 §3 檢定過的訊號,因此一概不做,而且這幾條與 §1–§5 一樣不得被「發現」後放寬:

- **不設門檻、不舉旗、不下判語。** 一旦輸出「今天不尋常」,它就是一個資訊性主張。
- **不算比率、不算百分比、不算淨額、不給總數。** 只給計數,除法與加法由讀的人做
  (§1 那五個整數的同一條紀律)。「增加減去減少」是一個分數的雛形,而分數會排名。
- **不排名契約**(§5)。payload 裡連契約代碼都沒有。
- **UI 只複述計數。** 沒有「偏多 / 偏空」,沒有解讀。

**`undetermined` 為什麼必須被數出來**:判不出方向的契約(當天或前一日沒有列、未平倉是
NULL)若被丟掉,四個計數的和會悄悄變成一個與契約數無關的數字,「今天 118 個契約增加」
讀起來就像一個涵蓋全體的事實,而實際上今天可能有 92 個契約根本沒有答案。成因依 R1 有
三種不可分辨,所以**只數,不分類**,也絕不說成「沒有變動」——不知道不是沒有變動。

**為什麼是一個平行的頂層鍵,而不是住進 `futures_volume_anomalies_meta`**:

- meta 依 §7.11 是「**這份名單的**隨附事實」,而這四個計數不是名單的事實:名單只有舉旗
  的契約,計數涵蓋全部 320 個,兩者的母體不同。
- 兩個鍵的**缺席條件也不同**。名單會因為 R4 算不出結算窗口而整個不主張(§7.13),而
  未平倉的方向與結算窗口毫無關係——跟著消失是連坐。測試鎖住那一天名單缺席而計數仍在。
- §7.11 的「meta 只有 `window_days` 一個整數欄位,它不是名次或評分的落腳處」這句話,
  只有在 meta 不接受新欄位的時候才有力量。那個鎖(`sorted(meta) == ["as_of",
  "window_days"]`)因此原封不動。

**三態**,與這個切片每一個鍵同一個約定:**沒有這個鍵** = 沒有算過(沒有期貨行情日);
**有鍵** = 數過了,**即使四個數字全是 0**(例:唯一的契約判不出方向)。兩者不可塌成
同一種表示——那是把「不知道」講成「今天一個契約都沒動」。

**來源**:方向一律由 `futures_volume_battery.oi_change()` 本人決定,與個股卡片上那個
數字是**同一次**計算的同一份結果(export 只算一次 `oi_changes`,一份餵個股、一份餵計數)。
在這裡自己再數一次「昨天」就會有第二個可以漂走的真相,同 §7.14 的理由。

**UI**:首頁「期貨異常」分頁,在名單**之上**。理由是那一頁最常見的狀態是空名單,而這
四個計數每一天都有內容;放在名單下面,它會在讀者最需要它的那一天被一段置中的「今天
沒有契約舉旗」擋住。文案一句,句號結束:

> 「期貨 {as_of} 未平倉較前一個期貨交易日:增加 {n} 個契約、減少 {n} 個、持平 {n} 個、
> 無法判定 {n} 個。」

「無法判定」那一項即使是 0 也照樣講——省略它會讓另外三個數字讀起來像涵蓋全體。

**閘門**:`test_payload_cannot_silently_gain_a_rate` **未修改**(它走的是個股的 `futures`
區塊),`test_the_index_cannot_silently_gain_a_rate` 也未修改(它走的是市場層級的名單)。
**兩者都照不到這個新鍵**——它是 `radar.json` 的第三個入口。所以另補一把走這個鍵的閘門,
`RANK_ISH + RATIO_ISH` 兩組都過,外加一個「鍵就是一個日期加四個整數」的形狀鎖。
