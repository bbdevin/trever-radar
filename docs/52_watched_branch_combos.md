## 1. 需求(使用者原話,2026-10-19)

「每日可以把 富邦新店 永豐金內湖 元大松江 這三個排列組合 就是至少要有富邦新店買超的股票 如果有加上元大松江的也一同買更好 就是可以按下按鈕去篩選增加 然後每天推播到我的自選 有一個小tab 就是類似特定籌碼分點 之類的 用意 只是更快速得到 今天有沒有這些人的動向 自己去抓給我 看到 然後 賣超也要 我也希望說 可以買的張數或是還持有的張數很多也要都列出來」

解讀:

- 自選頁多一個分頁「特定分點」,看**使用者自選的一組分點**今天的動向。預設 富邦-新店(主)、永豐金-內湖、元大-松江(正式 `branch_dim` 名稱已核對)。可搜尋加入其他分點(最多 6 個)、移除、點名稱換「主」。
- 買超:至少主分點買超;其他分點也同步買超的排前面(三家都買 > 主＋一家 > 只有主)。按鈕切 `主分點買超`／`主＋任一同買`／`全部同買`／`任一分點買超`(最後一個不要求主分點)。賣超鏡像。
- 列出今天張數、金額(估)、每個分點的**估計仍持有**張數與進場日,可依它排序;持有很多的標出來;另有「估計仍持有」檢視列出今天沒動、但仍持有很多的股票。
- 「每天推播到我的自選」:分頁每天隨資料自動換成最新一日,分頁標籤帶今天有進出的檔數。v3.10 時**不做手機通知**;2026-10-20 另案以 ntfy 做(不是 PWA push,見 §9)。

## 2. 資料契約:`branches/watch/`

export-json 的個股迴圈本來就逐檔讀 2 年分點列(`_branch_history_rows`,主鍵範圍);`BranchWatchCollector.add_stock` 在同一迴圈裡就地摘要,**不另掃 `branch_trades_raw`**。迴圈前只多兩條小查詢:最新現股分點日(覆蓋索引倒著找,`LIMIT 1`,6 碼權證列不算——權證分點可能先到)與 60 交易日下緣。程式:`pipeline/radar/export/branch_watch.py`。

`index.json`

```json
{"version":1,"as_of":"2026-10-16","window_days":60,"window_from":"2026-07-21",
 "shards":64,"hold_min":100,"hold_floor":20,"hold_top":60,
 "coverage":{"covered":1688,"expected":1957,"complete":false},
 "branches":[["富邦-新店",60,6,2,12,12], ...]}
 // [名稱, 分片, 當日買超檔數, 當日賣超檔數, 當日沒出現但估計仍持有(已輸出)檔數, 同上(截斷前)]
```

`coverage`(全部照匯入端,不另推;2026-10-19 verifier 第二輪修正):

- `expected` = `importer._branch_stock_pool(as_of)` 的檔數——直接呼叫同一個函式:當日有收盤、active 的**普通股**,**不含 ETF**(匯入端從不抓 ETF,`daily-branches.sh`「不含 ETF」)。`covered` = 池裡 `as_of` 已有任何分點列的檔數(個股迴圈本來就知道,零額外查詢)。
- `complete` = 匯入端把當日記為完成:`import_logs` 有一輪 `dataset='branch'` status=`ok`,且同一輪(同一個交易寫的 `branch_coverage` 列,`run_at` 相差 ≤ 10 s)的 `expected=N` ≥ 池大小。status=ok 的意思是那一輪每個目標都有答案(有列,或經別站確認的空,`_confirm_empties`)、failed=0、覆蓋率不低於 0.8 警報線;`--top 80`/`--ids` 的局部輪不算。(2026-10-20 `docs/47` §8.10 兩段式抓取起:股票段的 `branch` 列 failed 只算股票——以前權證抓失敗也會把這一列記成 incomplete、讓本頁誤標「尚未匯入」;權證段另記 `branch_warrant_pool`,不寫這兩列,本頁不讀它。)分點在 ≥50% 覆蓋就會上線(2026-09-16 17:40 輪 86%、09-17 46% 被扣留),第二輪約 22:00 才補齊,所以 17:40 輪常是 incomplete。
- 當日沒有任何分點匯入紀錄(本機/測試庫、import_logs 被 prune)→ 視為完成:沒有證據時不宣稱「待補」。
- 完成時,池裡沒列的 ~2% 是確認空(冷門股當天沒有分點成交),**不出提示、也不標待補**。只有 `complete=false` 且 `covered < expected` 時頁面才出琥珀提示。

`branches` = 近 60 交易日在任一現股/ETF 出現過的分點(停業 `CLOSED_MARKS` 排除),依名稱排序;也是前端「加分點」搜尋清單。

`s00.json` … `s63.json`(分片 = `int(sha1(名稱)[:8], 16) % 64`;64 片永遠都寫,舊檔每次清掉)

```json
{"version":1,"as_of":"…","window_days":60,"window_from":"…","shard":60,
 "branches":{"富邦-新店":[["2330",170,50,120,320,"2026-10-02",4,120,"2026-10-16"], ...]},
 "stocks":{"2330":["台積電",1069.0,0.09,30000,1]}}
```

- 列 = `[代號, 當日買張, 當日賣張, 當日淨張, 估計仍持有, 進場日, 視窗內出現天數, 視窗內淨張合計, 最後出現日, 均價(估)]`,依代號排序(第 10 欄 2026-10-20 加,見 §8.5;舊檔沒有)。分片另有 `warrants` 鍵、index 另有 `warrant` 鍵(§8)。
- 收哪些列:當日有出現的 (分點, 股) 全收;當日沒出現的收估計仍持有 ≥ `hold_min`(100 張),**或** ≥ 該股 20 日均量且 ≥ `hold_floor`(20 張)——與前端「持有量大」同一條規則,小型股 80 張 vs 均量 30 張也看得到(2026-10-19 verifier)。每分點最多 `hold_top`(60)檔、依持有張數由大到小取;被截掉時 index 第 6 欄 > 第 5 欄,畫面寫「共 N 檔,只列持有最多的 60 檔」。
- `stocks` = 該分片用到的股:`[名稱, 收盤, 漲跌%, 近 20 日均量張, 今天狀態]`,取不晚於 `as_of` 的最後一根;漲跌用還原價(`close × adj_factor`),除權息日不算跌。今天狀態:1 = 這檔 `as_of` 有任何分點列;0 = 匯入池的股票、今天沒列、當日匯入未完成(尚未匯入);2 = 今天沒列也不會再補(匯入已完成的確認空,或 ETF 等不在匯入池)。舊檔沒有這欄,前端當作 1。
- 同名不同 `branch_key`(不同來源頁)同一天合併,與 `branches/track` 以 `branch_name` 聚合同口徑。
- 逐位元可重現(全部明確排序),`export_parity.py` 新舊 code 對同一庫:其他檔全部 IDENTICAL/TIMESTAMP,只多這 65 檔。

## 3. 估計仍持有(誠實規則)

分點列只有「當天進入該股前 15 大買超或前 15 大賣超」才存在。

- **當日欄位**:當天沒有列 → `null`,**不寫 0**。null 依個股的今天狀態分三種(2026-10-19 verifier 兩輪修正):
  - 這檔今天有分點列,選的分點不在裡面 → 「未進前 15 大」(事實)。
  - 匯入池的股票、今天沒列、當日匯入未完成(17:40 輪可能只匯一半)→ 「尚未匯入」(未知)。這些股票不會出現在買超／賣超篩選裡,所以頁面上方用琥珀框寫「MM/DD 分點已匯入 X / Y 檔,其餘待下一輪更新…」,不讓它們無聲消失。
  - 今天沒列也不會再補:匯入已完成的確認空,或 ETF 等不在匯入池 → 「無分點資料」。
- **估計仍持有**:從 60 交易日視窗起點的 0 開始,逐日加淨張;賣超大於已知買超時歸 0(更早的部位未知,不往負的推;與 `docs/51`「出清清空」同口徑)。**進場日** = 最後一次由 0 轉正那天,**只看得到視窗內**:視窗以前就持有的部位,進場日會落在視窗起點那段,不是真正的第一次買超日。看不到的賣超扣不到,所以實際可能較少——畫面一律標「估」,頁尾常駐說明(`HONESTY_NOTE`)。
- **同名分點**:同一個 `branch_name` 有多個 `branch_id`(不同來源頁、改名合併)時,同一天的買／賣／淨張加總,與 `branches/track` 以名稱聚合同口徑。
- **為什麼 60 交易日**:約一季,涵蓋這類分點常見的波段持有;更長的窗口累積更多「沒進前 15 大的未知日」,高估更嚴重;20 日則太短,看不出已持有一段時間的部位。`branch_history_rows` 本來就讀 2 年,改窗口不增加 I/O。
- **金額(估)** = 張數 × 收盤 × 1,000。
- **持有量大**:估計仍持有 ≥ 1,000 張,或 ≥ 該股近 20 日均量(一整天的量)且 ≥ 20 張(地板,避免 3 張 vs 均量 2 張也被標)。前者抓大型股的大部位,後者抓中小型股相對其流動性的集中;只是醒目標示,不是判定。
- 禁用詞(勝率 獲利 報酬 關鍵分點 大漲 噴 極品 機率 目標價 買進 賣出 看多 看空 將會 有效支撐 壓力沉重 做多 做空 建議 喊單 套牢)由 `web/lib/watchedBranches.test.ts` 以字碼檢查。

- 本機永遠有一份 `localStorage` `watched_branch_set_v1`;登入且 `app_profiles.status = 'approved'` 時再讀寫 Supabase `watched_branch_sets` 自己那一列(每人一列:`branches text[]` 1–6 個、`anchor`、`updated_at`)。程式:`web/lib/watchedBranchSync.ts`(純邏輯＋同步器,`node --test` 可測)、`web/lib/watchedBranchSet.ts`(React hook,接 `lib/supabase.ts` 同一個 publishable key 客戶端與 `useSession`)。
- **SQL 執行前**:讀那張表會拿到 404(`PGRST205`)→ 這次頁面載入停用雲端、不重試、不寫 console,組合照舊存本機。每次整頁載入只會多一個 GET(瀏覽器自己會記一行 404 網路錯誤;站內換頁不再打)。

### 6.1 合併規則(`watchedBranchSync.ts` 檔頭;測試 `watchedBranchSync.test.ts`)

本機紀錄 = `{branches, anchor, edited_at, dirty, uid}`(`branches`／`anchor` 留在最上層,舊版程式照樣讀得懂)。`dirty` = 本機改動還沒確認寫上雲端;`uid` = 這份組合屬於哪個帳號(null = 從沒和帳號同步過)。

| 登入時的情況 | 結果 |
|---|---|
| 雲端有一列,本機沒有未上傳的改動 | **雲端勝**,覆蓋本機 |
| 雲端有一列,本機有未上傳的改動(本人或從沒同步過),且本機改動時間 > 雲端 `updated_at` | **本機勝**,立刻 upsert(離線、表還沒建、寫入失敗時的改動不會丟) |
| 同上但本機改動比雲端舊 | 雲端勝 |
| 雲端沒有這一列,本機有存過(本人或從沒同步過) | 用本機並上傳(第一次綁帳號;舊格式也是) |
| 本機是**別的帳號**留下的(同一台換人登入) | 雲端有 → 用雲端;沒有 → 照樣顯示、**不上傳**;本人改過之後才上傳本人的 |
| 本機什麼都沒存、雲端也沒有 | 預設組合,什麼都不寫 |

- 改動時間一定比它所根據的版本新(`max(現在, 上一版 + 1 ms)`),所以本機時鐘比別台慢也不會把新改動判成舊的。跨裝置的先後仍以各裝置時鐘為準(只影響本人那一列)。
- 寫雲端一次只送一個請求;送的時候又改了,送完再送最新那份。讀雲端期間改的,合併時以那份為準(不被讀回的舊值蓋掉)。
- 讀雲端期間有任何一次寫入成功(例如第一次 GET 還在飛,使用者改了、upsert 先完成)→ 讀回的那列可能是改動前的舊列,**整個丟掉不合併**,畫面與本機維持剛寫上去的那份;別台裝置的改動下次載入再拿(verifier 2026-10-20 回報,測試 `edit saved before the first cloud read returns…`)。
- 錯誤:表不存在(`PGRST205`／`42P01`／404)或沒權限(`42501`／401／403,例如帳號被改回 pending)→ 這次載入停用雲端;其他(斷線、5xx)→ 改動維持 dirty、下次改動或下次載入再試,整次載入最多 `console.warn` 一次。
已知取捨(皆低,只影響使用者自己的組合,不跨帳號讀到別人雲端的資料):

- **同一台換帳號丟未上傳改動**:A 帳號登出後有未上傳的改動、接著 B 帳號登入且 B 雲端已有組合 → 本機改成 B 的,A 那份未上傳的改動丟失(A 雲端仍是上次同步的版本)。登出不清本機(比照字級／主題)。
- **沒有主人的本機組合歸第一個登入的帳號**:舊格式(上線前存的)或登出狀態下改的組合 `uid = null`,這台裝置上第一個登入的已核准帳號會把它當成自己的——雲端沒有列就上傳到他的帳號,本機較新就蓋過他的雲端。共用裝置上,前一個人留下的組合可能被下一個人帶走(本來就在這台的 localStorage 裡、誰都看得到)。之後 `uid` 綁定該帳號,別的帳號不會再上傳它。
- **`updated_at` 由前端帶入(裝置時鐘)**:跨裝置的先後以各自時鐘判斷。時鐘偏快的裝置寫的列時間較晚,另一台時鐘正常的裝置之後**離線**改的組合可能被判為較舊、登入時被雲端蓋掉(線上的改動不受影響:改了就立刻 upsert,last-write-wins)。改由 DB trigger 蓋 `now()` 也只是把比較對象換成伺服器時鐘對本機時鐘,沒有本質更好,未採用。
- **空白判定兩邊不同**:SQL 用 `btrim`(只去半形空白),前端用 JS `trim()`(含全形空白 U+3000、NBSP 等 Unicode 空白)。前端比較嚴:前端存得下的,DB 一定收;反過來,有人繞過前端直接打 API 寫進「前後帶全形空白」的名稱,DB 會收,但前端讀回判為不合法 → 當作雲端沒有這列,用本機覆蓋上傳。只影響那個人自己的列。

### 6.2 SQL 資安審查(2026-10-20)

`docs/sql/20261019160000_create_watched_branch_sets.sql`(沿用原檔名:從沒執行過、名稱也沒有誤導,就地修正)。在本機 PostgreSQL 16 搭最小 Supabase 環境(anon／authenticated／service_role、`auth.uid()`、Supabase 的 default privileges,真的跑 `20260819171000_create_app_profiles.sql`)把整檔連跑兩次,46 項檢查全過:本人讀寫與 upsert、不能替別人寫／upsert／改／刪、不能把自己的列搬給別人、看不到別人的列、pending 讀得到也刪得掉自己的列但寫不進去、anon 對表與函式都 permission denied、每條輸入限制、重跑冪等、回滾後可重建。

| # | 草稿的問題 | 嚴重度 | 修正 |
|---|---|---|---|
| 1 | update policy 的 `using` 沒有 approved 條件(只在 `with check`),和既有三張表(`20261003181600`)寫法不同 | 低(`with check` 已擋住寫入;差在 pending 更新時是報錯而不是 0 列) | `using` 與 `with check` 都加 approved 子查詢,與既有寫法逐字相同 |
| 2 | 驗證函式 NULL／空陣列時回 NULL,check constraint 遇 NULL 會放行 | 低(`branches not null` 擋住了) | 整個判斷包 `coalesce(…, false)`,NULL 一律不合法 |
| 3 | 沒有 begin/commit,中途失敗會留半套 | 低 | 整檔包在一個交易裡 |
| 4 | 限制寫在 `create table if not exists` 裡,重跑時改過的限制不會生效 | 低 | 限制改成 `drop constraint if exists` + `add constraint`,重跑一定收斂 |
| 5 | 函式 execute 只收回 `public, anon`,沒照既有慣例先收回 authenticated 再授權 | 資訊 | 改成先全收回再只給 authenticated;已實測 check constraint 求值時寫入者需要 execute(收回後 insert 得 `42501 permission denied for function`) |
| 6 | 沒有回滾語句 | 資訊 | 檔頭加回滾(drop table＋drop function,交易包住) |

確認沒問題的:四條 policy 都 `to authenticated`、`auth.uid() = user_id`;寫入的 approved 檢查是 exists 子查詢、以呼叫者身分執行(受 `app_profiles` RLS 限制只看得到本人列,使用者無法自行改成 approved);主鍵 user_id → 每人一列,單列最多 6 × 64 字,不需列數 trigger;`watched_branch_names_ok` 是 SECURITY INVOKER、IMMUTABLE、`search_path = ''`、不讀任何表,沒有提權面——它因此也是 authenticated 可呼叫的 RPC,只回 true/false;anon 對表與函式皆無權限;`updated_at` 由前端帶入只影響本人那列的合併,不是稽核欄位。

剩下的低風險(不修):①名稱只擋控制字元,沒擋零寬字元或雙向控制字元(U+200B、U+202E 等);資料只有本人看得到、只以 React 文字節點渲染,最多讓自己的畫面怪,不跨使用者。②函式在 `public`,PostgREST 會把它列成 RPC;要藏就得搬到不對外的 schema,和現有慣例不同,不值得。

## 8. 權證同買／同賣與均價(估)(2026-10-20,v3.11;程式完成於分支、未合 main)

### 8.1 需求(使用者原話)

- 「自選的特定分點 再幫我增加如果這些特定分點也有買權證 同買就整理出來 例如 富邦新店買雙鴻 永豐金內湖買權證雙鴻 這樣也算同買」
- 「可以預估平均成本更好」

### 8.2 規則(定案,`web/lib/watchedBranches.ts`)

| 分點今天在標的 X 的權證淨額(同一檔標的所有該類權證合計) | 算哪一邊 |
|---|---|
| 認購淨買 ≥ 100 萬 | **同買**(和買 X 現股同一邊) |
| 認購淨賣 ≥ 100 萬 | **同賣** |
| 認售淨買 ≥ 100 萬 | **同賣**(押 X 往下,與賣超同一邊) |
| 認售淨賣 ≥ 100 萬 | **不計**,只列出(灰色膠囊) |
| 牛熊證 | 不算(與其他權證頁同口徑;上游逐日序列本來就只有認購／認售) |

- 為什麼認售淨賣不計:認售淨賣的方向不明確(可能是減少先前的認售部位,也可能是別的原因),所以只列出、不算進任何一邊。認購淨賣照使用者要求鏡像算同賣。
- 同一分點可能同時在兩邊(例:現股買超、同時認購淨賣):兩個事實都列出,兩邊各算一次,不互相抵銷(張數與權證金額單位不同,沒有可信的換算)。
- **主分點只買權證也算「主分點買超」**:使用者的例子是「這樣也算同買」,權證是同一個方向的表態。按鈕列多一顆「含權證」(預設開,記在本機 `watched_branch_warrants_v1`,徽章跟著同一個值);關掉就回到只看現股,權證膠囊仍列在卡片上但不計。
- 門檻 100 萬(`WARRANT_MIN_AMOUNT`)= 權證分點明細門檻。上游 `_WarrantWindowScan` 只留「任一區間(1/2/5/30/120 日)全部權證合計 |金額| ≥ 100 萬」的 (分點, 標的) 配對,所以今天認購 ≥ 100 萬的配對一定在裡面,**例外**:同一天認購與認售(或牛熊)互相抵到合計 < 100 萬、且其他區間也都 < 100 萬時,這個配對不在上游,今天的權證看不到(測試 `test_call_put_today_threshold_and_same_name` 的註解)。低於門檻的權證進出一律不列、不算。
- 金額 = 權證淨張數 × 當日權證收盤 × 1,000(權證每張價值差很多,所以用金額不用張數);同名不同來源頁在 SQL `GROUP BY branch_name` 就合併;停業分點排除。

### 8.3 資料日(誠實)

權證分點與現股分點是兩條管線、可能不同時匯入。index 新鍵 `warrant`:

```json
"warrant":{"data_date":"2026-10-19","day":"2026-10-19","counted":true,"complete":true,"min_amount":1000000,"pool_turnover_min":1000000}
```

- 權證分點日 ≥ 現股分點日 → 取**現股那一天**(`day = as_of`)的權證(逐日序列裡本來就有),`counted=true`。權證比現股新時不拿明天的權證當今天。
- 權證分點日 < 現股分點日(權證晚一步匯入)→ 取權證最新那天,`counted=false`:前端膠囊寫「權證分點 MM/DD 認購 +320萬」(灰色、不計),頁面上方琥珀框「權證分點資料日 MM/DD,比現股分點 MM/DD 舊:權證進出只列出(標日期),不算進今天的同買／同賣,待下一輪更新」。
- 沒有權證分點資料 → `warrant: null`,畫面沒有「含權證」鈕。
- **權證那一段匯入不完整**(2026-10-20 verifier):import_logs 的 `branch_warrant_pool`(docs/47 §8.10,權證段每輪記一列 ok / incomplete / error)取那一天最後一輪;不是 ok → `complete=false`、`counted=false`:膠囊寫「權證分點 MM/DD 未完整 認購 …」、不計,上方琥珀框「權證分點尚未完整…待下一輪更新」。沒有紀錄(本機/測試庫、兩段式之前的日子)當作完整,與現股 `import_complete` 同一個原則。
- **收集範圍要在畫面上說**(2026-10-20 verifier):夜間權證池只收當天成交 ≥ 100 萬的認購／認售(**上市＋上櫃**;以前只有上市,上櫃標的如雙鴻當晚根本沒有權證分點列,已改,docs/47 §8.10 第 5 點),且分點要進該權證當天前 15 大。WARRANT_RULE／WARRANT_NOTE 寫明這兩個條件;個股摘要多第 6 欄(有權證資料時):1 = 這檔當天有權證進夜間池,0 = 沒有 → 卡片寫「權證:未收集(MM/DD 這檔沒有成交 ≥ 100 萬的認購／認售)」;權證日不是今天 →「權證:MM/DD 未收集(權證分點只到 MM/DD)」;不完整 →「權證:MM/DD 分點尚未完整,只列出不計」。不再沉默。
- 現股的覆蓋／尚未匯入邏輯(§3)不變。

### 8.4 匯出(不另掃)

- `json_export._export_warrant_branches(..., on_window=watch.add_warrants)`:`_WarrantWindowScan` 掃完、`PositionStream.finish()` 之後,把 `scan.daily`({(標的, 分點): [[日, 認購, 認售]]})與 `stream.summaries`(docs/51 持有摘要)交給收集器,收集器只取一天、只留 ≥ 門檻的。這段寫出的權證檔一個位元都不變(`on_window` 只讀)。
- 分片新鍵 `warrants`:`{分點: [[標的, 認購淨額, 認售淨額, 認購仍持有成本, 認購換算現股均價, 認售仍持有成本, 認售換算現股均價], …]}`(元;null = 沒有／未達門檻)。收:今天有權證進出的配對;以及 docs/51 有持有估算(仍持有成本 ≥ 500 萬,`SCREEN_MIN_COST`)**且**這個分點在這檔已有現股列(或今天有權證進出)的配對——只為了在卡片上順帶顯示,不讓權證持有單獨把股票帶進「估計仍持有」檢視。
- 只有權證、沒有任何現股列的分點也進 index(才找得到分片);標的的摘要(名稱、收盤…)也寫進那片的 `stocks`(收集器對每檔都留摘要,不只入選的)。
- `export watch:` log 多 `warrant_rows=… warrant_day=…`。

### 8.5 均價(估)

- 現股:分片列第 10 欄 `均價(估)`。方法 = `pnl-avgcost-v1`(docs/42 `branch_interval_pnl.simulate_pair` 同一套):買超日以當天收盤(還原到 as_of 尺度:`close × adj / adj_as_of`)當成交價加權;賣超依均價扣張數、不改均價;持有歸 0 就重來(與估計仍持有同一條歸 0 規則)。這段持有裡**任一買超日沒有收盤 → null**(不拿部分成本充數),畫面就不寫均價。只用看得到的前 15 大日子,所以是「估」。
- 畫面:每個分點的持有行下面「均價(估) 1,063.4 · 現價高於均價 +0.5%」(|差| < 0.05% 寫「約等於」)。估計仍持有檢視的卡片另有「合計均價(估)」(選的分點中均價已知者依張數加權;有分點均價未知時註明「部分分點均價未知,未計」),排序多一個「現價對均價(低→高)」(合計均價,沒有均價的排最後)。
- 權證:沿用 docs/51 `wpos-avgcost-v1` 的「仍持有成本」與「換算現股均價」(`avg_under`),不重算:「權證 認購 仍持有(估) 820萬 · 換算均價 95.3」。只有仍持有成本 ≥ 500 萬的才有(docs/51 篩選摘要的門檻);權證持有的資料日不是今天時加「(MM/DD)」。帳面 % 沒有放(卡片已夠長,權證分點頁有)。

- 內文最多 6 行:①`主分點買超 N 檔 · 全部同買 M 檔 · 主分點賣超 K 檔`(只有一個分點時不寫全部同買);②–④買超前 3 檔;⑤賣超前 1 檔;⑥說明行。股票排序 = 主分點有參與的在前 → 同步家數 → 金額(估)(現股張數 × 收盤 × 1,000 ＋算進這一邊的權證金額)→ 代號(同前端「同步家數」排序)。每檔只列有參與的分點:現股寫張數(`+820`、`−300`),權證寫 `權證認購+320萬`/`權證認售+150萬`;任一參與分點估計仍持有達「持有量大」規則(≥1,000 張或 ≥20 日均量且 ≥20 張)→ 行尾 `估計持有量大`。一行超過 60 字截斷加「…」。
- 說明行(誠實):`單位:張`;權證 `含權證(金額為估算)` / `權證分點只到 MM/DD,權證同買稍後更新`(第一段上線時權證還沒進來)/ `權證分點未完整,權證同買稍後更新` / `不含權證`(沒有權證資料);現股覆蓋未完成時 `分點已匯入 X/Y 檔`(與頁面琥珀框同條件)。今天都沒動 →「選的分點今天都沒有進入任何股票的前 15 大買超或賣超」。
- 禁用詞(§3 那一串)由 `test_watch_push.py` 對每種變體的訊息與模組全部字串常數檢查;不寫價位、不給任何操作意見。

### 9.3 時機與去重

- 接線:`daily-branches.sh` 的 `publish_site`(每次上線共用的那一份)在 `deploy_data`、`futures_digest` 之後 `watch_push "$ROUND_DATE"`。所以第一段上線(現股)後問一次、第二段上線(權證＋排行)後再問一次、22:30 第二輪若重新上線再問一次。休市日分點輪在上線前就收工;另外 `--expect-date` 擋住「export 的資料日不是本輪資料日」的情況(不送舊資料)。
- 「名單」= 主分點有參與、或至少兩家同步的 `(買/賣, 代號, 參與分點)` 集合(`moves`)。**名單沒變 = 不是實質變動**:張數、金額、持有估算變了都不再送。
- 同一資料日最多三則:`first`(當晚第一則,完整版)→ `warrants`(權證算進今天之後名單有變;只列名單有變的股票,「權證算進今天之後名單有變動:」)→ `late`(之後名單又變,例如 22:30 補齊覆蓋;「名單有變動:」)→ 不再送。權證算進來但名單沒變 → 不送第二則。`warrants` 與它的標頭只在「上一則送出時權證還沒算進今天、這一次才算進」時使用(狀態記 `counted`);第一段沒上線的日子(覆蓋率 < 0.98,唯一一次上線已含權證),之後的變動走 `late`、標頭「名單有變動:」,當天最多兩則。
- 狀態檔形狀不對(合法 JSON 但不是這個形狀,例如 `[]`、`0`、`sent` 是 list、`moves` 壞掉)與 JSON 壞掉一樣當作沒有狀態(新的一天):最壞多送一則,不會讓這一步每次上線都失敗。
- 狀態檔 `data/watch-push-state.json`(主機端寫、經 stdin 給容器讀;內容:資料日、組合、已送的種類、名單):**只在 ntfy 回 2xx 之後**才寫(tmp+mv)。送失敗 → 不寫,下一次上線重試。狀態壞掉/不同資料日/組合換了 → 當作新的一天。重開機不會清(在 `data/`),22:30 那輪讀得到。
- 這一步**永不影響本輪**:60 s 送 TERM(`docker run --init`,容器裡的 python 收得到)、再 10 s 強制結束,最長約 70 s;產生失敗或送失敗都只 notify_warn 一則到維運主題,`return 0`。

### 9.4 人類要做的事(開通)

1. 產生主題名(在 VPS 或本機):`openssl rand -hex 16`,例如得到 `3f9c…`;主題用 `radar-watch-3f9c…`(任何長的隨機字串都可,**不要**用維運那個)。
2. VPS `vps/.env` 加一行 `WATCH_PUSH_NTFY_TOPIC=radar-watch-3f9c…`(不加引號)。要換組合再加 `WATCH_PUSH_BRANCHES=富邦-新店,永豐金-內湖,元大-松江`(第一個是主分點)。不用改 crontab。
3. 手機 ntfy App → 訂閱(+)→ 伺服器 ntfy.sh → 主題填同一個名字。
4. 預覽(合 main、VPS `sync_code` 之後;不送、不寫狀態):
   `cd ~/trever-radar && docker run --rm -v "$PWD/pipeline":/app/pipeline -v "$PWD/web/public/data":/app/web/public/data:ro radar-pipeline python -m radar watch-push --data /app/web/public/data --dry-run`
   (加 `--branches 元大-松江,富邦-新店` 試別的組合。)
5. 送一則測試(不看狀態與日期、不寫狀態檔,當晚的正式推播不受影響):
   `cd ~/trever-radar && bash -c 'source vps/scripts/lib.sh >/dev/null && watch_push --force'`
6. 關掉:刪掉 `WATCH_PUSH_NTFY_TOPIC` 那行(或留空)。

### 9.5 風險

- ntfy.sh 公開主題:**知道主題名的人都讀得到**(也能往裡面發訊息)。內容只有公開市場資料的整理,沒有帳號資訊;主題名要夠長、隨機、不貼到公開地方。若外洩:換一個主題名、手機重新訂閱。
- 推播的組合是 VPS 設定,不是 App 裡的組合(§9.1)。
- 頁面上的 `PUSH_NOTE`(「這裡不發手機通知」)沒有改:頁面本身確實不發;推播只對設定了主題的人(管理員)。

## 已知限制(verifier 2026-10-19 第三輪,皆低)

- **status=ok 不保證每檔都公布了**:匯入端在覆蓋率 ≥ 0.8、failed=0 時就記 ok;來源還沒公布、但多站一致回空的股票算「已答」。所以第一輪約 0.85–0.97 的晚上(如 2026-09-16 86%)會被當成完成,缺的股票顯示「今天無分點資料」、沒有「待下一輪」提醒,22:30 那輪補上後才有。當下文字為真,只是少了「還會再來」的提示。
- **當天最後一輪是 incomplete 時**,`complete` 會一直是 false,直到資料日往前推:提醒持續顯示,真的沒資料的股票會被標「尚未匯入」。
- **池在 export 時重算**:若匯入之後才補進 as_of 的報價,池變大、那一輪的 expected 不足,當天永遠不算完成(邊角情況)。
- `import_logs.run_at` 若混到沒帶時區的列,當台北時間處理(不再讓整個 export 因 TypeError 中止)。
