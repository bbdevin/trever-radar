# 39. 「隔天大漲」次數 —— 事前登記(統計量、否決條件、全案否決)

> **地位**:本文件是**事前登記**。效力來自時間順序:它必須在任何人對 `daily_scores` 的 `fwd_*` 欄位做過任何彙總、或把 `daily_scores` 與次日價格 JOIN 過之前 commit。撰寫當下,撰寫者與決策者都**沒有看過任何分布**——沒有看過任一漲幅的基礎率、沒有看過 `final` 與次日報酬的關係;看過的只有 `schema.py`、`performance.py`、`scores.py`、`json_export.py` 與 `vps/scripts/*.sh` 的程式碼。
>
> **凍結規則**:同 `docs/38` §0。本文件 v1 的每一個數字與每一條規則,在資料可見之後**不得修改**;要改只能開 v2,而 v2 只能用 v2 commit 之後才出現的交易日重新取得資格。
>
> **使用者原話**:「幫我規劃功能 就是隔天大漲機率」。本文件把「隔天大漲」翻成一條可重現、**買得到**、無分母的事件;把「機率」翻成**一對計數加上它自己的基準**;把「這個功能該不該存在」翻成一個能證偽的檢定。
>
> **與兩個先例的關係**:`docs/04` §2 的往後看方向(n=18、1.81σ)什麼都沒上線;`docs/38` 的期貨量異常(|F_only|=680、十組 seed 全過)上線了。兩者的共同點是**答案在看資料之前就寫死**。本功能是本產品會做的最具預測性的主張,所以它走的是同一條路,而且門檻**只多不少**。
>
> **先講清楚一件事,免得日後被拿來放寬 30**:`compute-scores` 於 2026-07-07 建立(git),只寫最新一天、從未回補,所以第一次執行時樣本大約只有 55 個市場日(設計時的估計值;commit 前實測為 **49** 個,見 §9,比估計更少、方向相同)。**第一次跑出「檢定力不足」是正常結果**,依 §3.7 累積 60 個新市場日後重跑;不是放寬門檻的理由。

## 0. 名詞

- **市場交易日曆 D**:`daily_prices` 任一列存在的日期集合(同 `docs/38` R4 的市場日定義)。
- **評分列**:`daily_scores (s, t)`。母體由 `scores.py` 決定:`stocks.type = 'stock'`、20 日均成交金額 ≥ 30,000,000、t 有價格列、`combine()` 非 None。列是**凍結的**(`docs/04` §12 前瞻記錄法):`compute-scores` 只寫最新一個價格日(`scores.py:431-435`),沒有任何腳本重算歷史(`repair-window.sh` 步驟 1–4 不含它)。但同一天的列會在 15:00 / 16:10 / 17:40 / 21:20 / 23:30 隨資料到齊被覆寫;**紀錄之列 = 最後一版**,即次日開盤前最後發佈的那一版。
- **上榜 (s, t)**:與 export 逐字相同(`json_export.py:1079-1088`):`final ≥ 65`,依 `(final, branch_score(None 視為 −∞), turnover)` 由大到小排序,取前 40。第 40 名若三個鍵完全同分,**同分者一併視為上榜**(export 的穩定排序依輸入順序決定,那個順序不可重現;含入是唯一不需要猜的選擇),數量記錄為 `tie_at_cap`。
- **上榜事件 L**:同一檔股票在**連續市場交易日**上榜的一段,取**首日**(`docs/04` §5「連續日合併為一次事件,以首日計」)。中間某個市場日該股沒有 `daily_scores` 列或不上榜,段落即中斷。
- **進場日 e(t)**:D 中 t 之後的**第一個**市場交易日。由日曆算,**不從**儲存的 `entry_date` 讀(那一欄是 §2 R2 的對照,不是來源)。
- **進場價 / 出場價**:`daily_prices.open(s, e)` 與 `daily_prices.close(s, e)`,**原始價、不乘 `adj_factor`**。同一列的兩個價,因子相消;用原始價是把「這個統計量與還原因子無關」變成結構事實(2026-09-03 的事故就是還原因子錯了兩個月沒人發現)。
- **命中 hit(s, t)**:`100 × close(s, e) ≥ 107 × open(s, e)`。白話:**次一交易日以開盤價買進、以收盤價計,漲幅至少 7%**。
- **兩組對照** P_stock、P_date:見 §3.3。

## 1. 統計量:一對計數,與它自己的基準

**隨功能一起輸出的事實(全部是整數或日期,沒有比率、百分比、機率、均值、名次)**:

| 欄位 | 內容 |
|---|---|
| `from` / `to` | 計數涵蓋的第一個與最後一個事件日 |
| `events` | 成熟且未被 §2 否決的上榜事件數 n |
| `hits` | 其中命中的事件數 h_L |
| `placebo_stock_hits` `{min, max}` | P_stock 十組 seed 的命中數最小值與最大值 |
| `placebo_date_hits` `{min, max}` | P_date 十組 seed 的命中數最小值與最大值 |
| `threshold_pct` | 恆為 7,從模組常數讀出,不在前端寫死 |
| `leg` | 恆為字串 `"entry_open_to_close"`,讓讀者知道量的是哪一段 |

使用者看到的是「上榜 1,240 次、命中 96 次;同一批股票沒上榜的日子等量抽 10 組命中 41–58 次;同一天沒上榜的其他股票等量抽 10 組命中 37–55 次」,除法由人做。**基準一定跟著計數走**:單獨一個 96/1,240 會被讀成一個機率,而一個沒有基準的機率沒有意義——它是高還是低,只有跟「沒有訊號的日子」比才知道。min–max 是整數,不需要 σ,也把抽樣的不確定性帶給讀者。

**為什麼是 7% 與「開盤到收盤」,而不是其他候選**:

| 候選 | 為何不採 |
|---|---|
| 收盤對收盤 ≥ 7%(板面漲幅) | 含前一日收盤到開盤的跳空,那一段沒有人買得到;開盤就鎖漲停的日子會算成 +10% 的命中。它是「大家會下注的數字」,卻是拿不到的數字。**只作報告用的伴隨計數(§3.6),不作統計量。** |
| 漲停(≥ 9.5%) | 買得到的版本是「從非漲停的開盤價收在漲停」,比 7% 更稀少;而 7% 在開盤到收盤這一段本來就已接近它。 |
| 波動率縮放(k × ATR、z) | 每檔股票一個除數;低波動股 3% 就成了「大漲」,那不是使用者說的字。波動率的干擾由 P_stock(同股對照)吸收,不由重新定義事件吸收。 |
| 3% / 5% / 6% | `docs/04` 裡有這些數字(W3 的 3%、追高警示的 6%),但沒有一個叫「大漲」。 |
| **7%,開盤到收盤(採用)** | 7% 是 `docs/04` §13 `S1_REBOUND_RELAXED`「近 20 日曾大漲 ≥7%」——本專案唯一把「大漲」寫成數字的地方,與 `docs/38` 借用 1% 是同一個動作。「開盤到收盤」是 `docs/04` §12「以次日開盤價為進場基準,誠實計算,不用當日收盤自欺」——本專案既有的往後量規則,`performance.py` 實作的正是它。 |

**已知代價,事前承認**:跳空 +3% 再鎖漲停的日子,開盤到收盤約 +6.8%,**不算命中**。在這條規則下「大漲」的意思是「收盤比你買得到的價位至少高 7%」。這個代價的方向是**命中變少**,而且兩臂受同樣的規則。

## 2. 否決條件(per 事件、per 對照日;命中任一條 → 該日兩臂都不進,也不算未命中)

### R1 進場日不成熟或無列

- `e(t)` 不存在(t 之後 D 裡沒有日子)或 `e(t) > as_of`;或 `(s, e)` 沒有 `daily_prices` 列;或 `open` 為 NULL / ≤ 0;或 `close` 為 NULL。
- 不進分母、**也不算未命中**(`docs/38` §3.1 與 §6 修訂 2 同一條)。成熟性看 `daily_prices`,**不看** `fwd_20d` 是否已填——`compute-performance` 在 `fwd_20d` 填上之前會持續重訪該列,那是它的完成條件,不是本檢定的。

### R2 儲存欄位不一致(重用的完整性閘門)

- 儲存的 `entry_date ≠ e(t)` → `R2_entry_shifted`。`forward_returns` 會跳過缺列或開盤為 0 的日子往後找(`performance.py:47-51`),於是缺了 t+1 的列時 `fwd_1d` 講的其實是 t+2;而列一旦有了 `fwd_20d` 就不再重訪,缺口事後補上也不會自己修正。
- 儲存的 `fwd_1d` 為 NULL,或 `|fwd_1d − 100 × (close/open − 1)| > 0.01` → `R2_fwd_mismatch`(0.01 是儲存值四捨五入到兩位的容差)。
- **補救方式是整表 `compute-performance --all` 加一個新的執行次數**,不是逐列修、也絕不改用儲存值來評分——同 `docs/38` R1「修補整市場缺日的方法是重跑回補,不是放寬本條」。

### R3 鎖漲停:**不是否決**,是結構性未命中

開盤即漲停的日子,開盤到收盤 ≤ 0,依定義不命中——方向是保守的,而且兩臂相同。**只報告**:`entry_open_at_limit_proxy` = 進場日 `open(s, e) ≥ 1.095 × close(s, t)` 的事件數(9.5% 是 S1 嚴謹版的漲停代理;升降單位的進位不建模)。

### R4 個股身分

`stocks.type ≠ 'stock'` 不在母體(`scores.py` 已擋)。

### R5 已知盲點(記錄,v1 不處理)

- **處置股**:`docs/04` §0 說要排除,但 `schema.py` 沒有任何處置/注意股的表,程式沒有排除。處置股分盤撮合,開盤價的可得性與一般股不同,偵測不到。
- **同一天的列被覆寫多次**:讀者在 15:00 看到的榜(分點 35% 尚未到)與 23:30 的紀錄之列可能不同;15:00 那一版沒有被存下來。偏誤方向不明。v2 若要修,是在發佈時凍結一份 `published_final`,那是 schema 變更,不在本文件內。

## 3. 全案否決(過不了就整個功能不上線,不是「上線但加註」)

### 3.1 樣本

- **as_of**:`daily_prices` 的最大日期。
- **評估期**:`daily_scores` 的第一個日期到 as_of。
- **L**:全部通過 §2 的成熟上榜事件,n = |L|,h_L = Σ hit。
- **對半**:評估期內的市場交易日依 `branch_window_direction_battery.split_window` 的慣例對半切(依交易日切,奇數多的一天歸後半),記為 H1、H2。每個事件與每個對照日依其 t 落入一半。

### 3.2 檢定 A:檢定力(純計數)

`n ≥ 30` **且** `h_L ≥ 30`(`LOW_SAMPLE_SURVIVORS`,沿用 `branch_window_direction_battery.py:126`)。

不足 → **UNDERPOWERED**,是**檢定力不足的無結果,不是否證**;依 §3.7 重跑。為什麼數的是 h_L 而不只是 n:n 依構造會很大(每天最多 40 檔乘以天數),讀者拿去除的分子是 h_L,而一個小於 30 的分子就是小分母陷阱搬到樓上。

### 3.3 檢定 B:資訊性(兩組計數配對的安慰劑,每一組每一個 seed 都要過)

**假設**:上榜這件事,對「次日開盤買進收盤計漲 ≥ 7%」的發生次數,有超出 (a) 該股自身、(b) 當天市場 之外的內容。兩個干擾各配一組對照。

- **P_stock(同股、同半段)**:對每一個 (股票 s, 半段 h),若 s 在 h 有 k 個事件,從 `pool_stock(s, h)` 不放回抽 k 天。`pool_stock(s, h)` = { (s, d) : d ∈ h,有 `daily_scores` 列,**不上榜**,R1 與 R2 通過 }。依半段配對是為了 §3.4 能在每一半內比較;整體自然也配對。
- **P_date(同日、其他股票)**:對每一個有 k_t 個事件的日期 t,從 `pool_date(t)` 不放回抽 k_t 列。`pool_date(t)` = { (s′, t) : 有 `daily_scores` 列,**不上榜**,R1 與 R2 通過 }。
- **seed 固定為 0..9 共 10 組**,兩組對照各自抽。抽不滿任一個 (s, h) 或任一個 t → **NOT EVALUABLE**,JSON 逐項列出 `(stock_id, half, k, pool_size)` 或 `(date, k, pool_size)`(`docs/38` §6.5 的報告義務)。
- **判準(形式沿用 `docs/38` §3.3)**:對每一組對照、每一個 seed,令 `p̂ = h_P / n`,`σ_P = max(1, sqrt(n · p̂ · (1 − p̂)))`,必須 `h_L − h_P(seed) ≥ 2 · σ_P`。**20 個判準(2 組 × 10 seed)任一不過即不過**。「換 seed 直到過關」是 seed 要暴露的失敗模式。
- **刻意不從池子排除的日子**:「次日是該股上榜日」的日子。它們是**沒有訊號卻大漲**的日子——正是基礎率本身;排除它們等於把大漲從對照組裡拿掉,方向是**朝著過關**。這一條事前登記為不可用的補救:檢定 B 失敗後,「池子被隔天上榜的日子汙染」不能當重做的理由。

### 3.4 檢定 C:跨半段一致性(只看正負,不是第二個顯著性檢定)

對每一半 h ∈ {H1, H2}、每一組對照、每一個 seed:`h_L(h) − h_P(h) > 0`(嚴格大於)。P_stock 依 (股票, 半段) 配對、P_date 依日期配對,所以兩臂在每一半內本來就是等量的。C 的工作只有一個:擋下「全部的優勢來自某一個月」。它會讓一個真的但很小的效果過不了——而一個只在半段成立的「隔天大漲次數」本來就不該讓人拿去下注。

### 3.5 裁決與紀錄

- A 過 **且** B 的 20 個判準全過 **且** C 全過 → **上線**(§4 步驟 5)。
- 其餘一律**不上線**;NOT EVALUABLE 對 §3.7 的重跑規則算**無結果**。
- 每次執行寫入 `docs/STATUS.md`:本文件 commit hash、as_of、`daily_scores` 首尾日期與日期數與列數、n、h_L、每一組對照每一個 seed 的 `h_P / σ_P`、H1/H2 的邊界與每半的 h_L / h_P、各否決計數、`tie_at_cap`、§3.6 的伴隨計數、裁決、第幾次執行。

### 3.6 伴隨計數(**只報告,永遠不是判準,永遠不是補救**)

- `board_hits`:`close(s, e) × adj(e) ≥ 1.07 × close(s, t) × adj(t)` 的事件數(板面漲幅版;**這一個依賴 `adj_factor`**,跨兩列,標明)。
- `board_hit_not_entry_hit`:板面算大漲、本規則不算命中的事件數——「你看到了但買不到」的數量。
- `entry_open_at_limit_proxy`(R3)。
- `over_cap_days`:`final ≥ 65` 但被 40 檔上限切掉的股票日數;`tie_at_cap`。
- `all_days_events` / `all_days_hits`:不合併連續日的版本(每一個上榜日都算),讓讀者看見合併砍掉多少。
- 依月份的 `events` / `hits`;依 `final` 區間(65–74、75–84、≥ 85)的 `events` / `hits`。這兩項**只在 battery JSON**,不進匯出。

### 3.7 不允許的補救(在看到資料之後)

- 改 7、改 65、改 40、改 30、改 2σ、改 seed 清單、改 0.01、改「開盤到收盤」這一段、改 1 日、改「連續日取首日」、改兩個池子的定義、改對半規則、改 C 的正負判準。
- 把統計量換成收盤對收盤、5%、`fwd_3d` / `fwd_5d`、依 reason code 或分數區間條件化、每檔股票各自一個數字——那是 v2,只能用 v2 之後的交易日。
- 用第二個往後看量「補救」B 或 C。允許探索、允許寫進 STATUS,**不允許改變裁決**。
- **重跑頻率**:無結果時,累積 ≥ 60 個新的市場交易日才可重跑一次;每次重跑記次數。兩次執行之間若做過資料修補(`compute-performance --all`、報價缺口回補),下一次執行仍是新的次數、同一套規則。

### 3.8 上線之後

- 匯出每晚用**同一個函式**、從 `from` 起累計重算那幾個整數(同 `docs/38`:export 與 battery 共用同一條規則,export 自己重寫一次就是第二條規則)。
- 每 60 個市場交易日以累計樣本重跑 battery;B 任一 seed 或 C 任一項不過 → **撤下顯示**,數字留在 JSON(同方向 battery 的撤回規則)。
- `final` 的組成、權重、65 門檻、前置過濾任一改變 → 計數**從改變日重新開始**,並依 v2 規則重新取得資格。這個計數是關於**一條規則**的主張,不是關於「某個叫綜合榜的東西」。

## 4. 執行順序(每步之間不看資料)

1. Commit 本文件,把 hash 記進 `docs/STATUS.md`。**在此之前不對 `fwd_*` 做任何彙總,不把 `daily_scores` 與次日價格 JOIN。**
2. 只記錄涵蓋度:`daily_scores` 首尾日期、日期數、列數(這幾個數不是 §1–§3 任何門檻的輸入)。
3. 前置實作(不需看資料):`pipeline/radar/compute/next_day_surge_battery.py`,唯讀(`mode=ro`、不呼叫 `init_db()`、不寫任何一列),風格同 `futures_volume_battery.py`;`LOW_SAMPLE_SURVIVORS` 從 `branch_window_direction_battery` **import**、`PLACEBO_SEEDS` 與 `seed_result` 從 `futures_volume_battery` **import**(不複製第二份 30、第二份 2σ);測試用發明的 fixture;比照 `test_futures_export.test_payload_cannot_silently_gain_a_rate`,對新的 `radar.json` 鍵補一把 `RATIO_ISH + RANK_ISH` 閘門,外加一個「就是 §1 那幾個鍵,全部整數或日期,沒有第 N+1 個」的形狀鎖。
4. 跑 battery 一次,把 §3.5 的紀錄寫入 STATUS。
5. **只有在 PASS 之後**:`radar.json` 加一個平行的頂層鍵 `list_next_day_surge`,內容就是 §1 表格。三態同 `docs/38` §7.5:**沒有鍵** = 沒算過(沒有主張);**有鍵** = 算過了。UI 只複述,句子由 `lib/` 的純函式產出,逐字鎖住:
   > 「{from} 至 {to},綜合榜上榜事件共 {events} 次;其中次一交易日以開盤價買進、以收盤價計,漲幅 ≥ {threshold_pct}% 的有 {hits} 次。同一批股票未上榜的日子等量抽樣 10 組,命中 {placebo_stock_hits.min}–{placebo_stock_hits.max} 次;同一天未上榜的其他股票等量抽樣 10 組,命中 {placebo_date_hits.min}–{placebo_date_hits.max} 次。」
   > 「這是次數,不是機率。不含前一日收盤到開盤的跳空;開盤即漲停的日子算未命中;每檔股票沒有自己的數字。」

   「機率」二字**不得**出現在鍵名或正面句子裡,只出現在風險句的否定裡。

## 5. 明確不做的事(v1)

- 不做每檔股票的數字。整體過關**不授權**個股主張:一檔上榜 3 次的股票沒有分母。
- 不依 reason / risk code、不依分數區間條件化匯出(§3.6 的區間計數只在 battery JSON)。
- 不做 3 / 5 / 10 / 20 日。
- payload 與 UI 任何地方不出現百分比。
- 不把收盤對收盤當標題數字。
- 不依「大漲可能性」排序任何股票。

## 6. 對六個問題的裁決(摘要,細節在 §0–§5)

1. **大漲** = 次日收盤 ≥ 1.07 × 次日開盤(7 來自 S1,這一段來自 `docs/04` §12)。不用波動率縮放;波動率由 P_stock 吸收。
2. **機率** → `hits` / `events` 兩個整數 + 兩組對照的整數 min–max。N/M 就是他們問的那個機率的最大概似估計;我們給 N 與 M 而不給 N/M,是讓分母可見;給基準,是因為一個沒有基準的機率讀不出高低。`strategy_meta` 有 `win_rate`+`samples` 的先例,本功能更嚴,理由是這個數字會被拿去下注、而它唯一誠實的讀法是相對於基準。
3. **條件** = 上榜(final ≥ 65 前 40,連續日取首日),整體合併。它是對榜單的校準陳述,會把排序啟發變成一個往後的主張——所以先過 battery,之後每 60 日重驗,不過就撤。不做個股、不做 code、不做區間。
4. **加了什麼**:過關時,加的是「相對於自身基準的次數」——`watch_price` 與裸的 `fwd_1d` 都給不了這個。不過關時什麼都不加,STATUS 記下「榜單沒有可量到的次日大漲內容」。
5. **漲停**:開盤到收盤這一段已結構性處理——鎖漲停的開盤是未命中(保守方向)。9.5% 代理只報告。處置股未在程式中排除,記為盲點。
6. **不上線的條件**:A(n ≥ 30 且 h_L ≥ 30)、B(兩組對照 × 10 seed,全部 ≥ 2σ)、C(兩半各自正號)。任一 NOT EVALUABLE 即不上線。

## 7. 儲存的 `fwd_*` 欄位可能哪裡錯(重用時要擋的)

- **進場日位移**:`forward_returns` 跳過缺列/開盤為 0 的日子,缺了 t+1 就講 t+2;有了 `fwd_20d` 後不再重訪,事後補齊的缺口不會自己修(2026-07-16..08-19 的 TPEx 缺口就是一次,09-19 才 `--all`)。→ R2 擋。
- **重訪中的列**:`fwd_20d` 為 NULL 的列每晚重算,`fwd_1d` 可能因為 candle 改變而改變。→ 成熟性看 `daily_prices`,不看 `fwd_20d`。
- **兩位小數**:6.996 存成 7.00。→ 判準用原始價的不等式,儲存值只作 0.01 容差的對照。
- **`adj_factor`**:1 日這一段結構上無關;3 日以上與 §3.6 的板面計數依賴它,而它 09-04 之前全市場為 1.0。→ 板面計數標明依賴,只報告。
- **母體與規則漂移**:缺口期間 TPEx 股沒有評分列(不是偏誤,是缺席);09-04 之前 `tech_score` 建立在未還原價上,`final` 的規則不是今天的規則。→ 計數是「已發佈的榜」的校準,不是「今天規則」的校準;§3.8 規定規則改變即重新起算。

## 8. 沒被問到、但會讓這件事不誠實的地方

- **同日多次覆寫**(R5):讀者 15:00 看到的榜與紀錄之列可能不同,方向不明。
- **40 檔上限**:`over_cap_days` 讓讀者看見「上榜」與「≥ 65」差多少。
- **存活偏誤**:進場日沒有 candle 的股票(停牌、下市)不進分母、也不算未命中;數量在 R1 計數裡。
- **相依性**:同股連續上榜由「取首日」處理;同日多檔一起漲由 P_date 與 C 處理;剩餘的群聚仍會讓二項 σ 偏樂觀——這是 C 存在的理由,不是被治好的問題。
- **7% 的來源**:它是借來的,不是推導的;正當性只在於現在定下來、之後不動。
- **字**:UI 不寫「機率」。使用者要的是機率,得到的是「發生了幾次、沒有訊號時發生了幾次、分母多大」——那是他們能誠實拿到的全部,而且比一個百分比更能回答「我該不該信這個榜」。
